# 22 细化 Template、组合链与可执行族

本文定义 KTA 的知识单元，以及它们怎样组合成可运行的 kernel。定义沿用论文第 2–4 节，并补上工程实现需要的部分。

## 1. 基本思路

论文的组织原则：**每一步细化，把一个粗的数据事务替换成若干更细的事务。** 例如：

- 一次归约 → 分组求部分和，再合并；
- 一个逻辑值 → 占用一个可复用的缓冲；
- 一次原子写入 → 一次发出，加上之后的一次完成；
- 一个缓冲 → S 个轮转槽，提前 P 个 tile 加载。

每一步都带来新的决策变量，也带来一条只有这一步才能表述的局部义务。

由此得到 KTA 的三个核心对象：

| 对象 | 是什么 | 粒度 |
| --- | --- | --- |
| **细化 Template**（下文简称 Template） | 一个带契约的细化步骤：把某种模式的粗事务细化成更细的事务，引入一个新的设计对象 | 细，一步 |
| **组合链** | 一串 Template 实例及其变量绑定，从 workload 一路细化到可执行程序 | 一个 kernel family 的完整设计 |
| **可执行族** | 组合链＋生成器代码：给定一组变量取值，生成一个可编译、可运行的 kernel | 一个 kernel family |

kernel 是可执行族的一次赋值。一个 kernel family 不是一个 Template，而是一条组合链。

## 2. 细化 Template

### 2.1 字段

论文的 Template 是元组 (O, X, C, Pre, P, π, Σ, Ĵ, Γ)。KTA 保留全部字段，再加上让它能被检索、组合、复用所需的字段。精确的 schema 见 [spec/schemas.md](../../spec/schemas.md)。

| 字段 | 内容 | 来源 |
| --- | --- | --- |
| level | 从哪一层细化到哪一层（论文的第 0–5 层） | 论文 |
| kind | 变化的类型：垂直细化、表示扩展、水平重写、限制或成本修订 | 论文表 4 |
| **refines** | 被细化的粗事务的**模式**（§2.2） | 新增 |
| **produces** | 细化后产生的事务种类 | 新增 |
| O | 新的设计对象：一个共享内存槽、一次异步传输、一个缓冲槽、一次资源绑定 | 论文 |
| X | 决策变量：名称、域、结构变量或数值变量、编译期或运行时、软件、硬件或边界 | 论文；绑定时机为新增 |
| C | 搜索约束：可执行表达式 | 论文 |
| Pre | 保持上一层语义所需的前提 | 论文 |
| P | 这一步在代码中的体现：各后端的参考代码片段 | 论文；片段为新增 |
| π | 反向映射：怎样把细化后的设计解释为细化前的设计 | 论文 |
| Σ | 证明义务的清单：每条的名称、陈述、计划的检查方式 | 论文 |
| Ĵ | 成本项：按硬件单元的工作量表达式，以及不能重叠的项 | 论文；按单元为新增 |
| Γ | 适用范围：对模式参数、workload 参数、硬件契约的谓词 | 论文 |
| **requires** | 需要的硬件能力 | 新增 |
| **relations** | 与其他 Template 的关系：requires、excludes、enables、refines、alternative_of | 新增 |
| ς | 结构签名：算法组织、复用方向、存储位置、边界模式、依赖的资源 | 论文 |
| **numeric_risk** | 是否改变数值，以及检查时必须加入的输入分布 | 新增 |
| **expected_sass** | 这一步在 SASS 中应留下的痕迹 | 新增 |

以下内容由工具从证据生成，作者不能写：卡片摘要、保证等级（§5）、复用统计、已知无效的条件。

### 2.2 模式：让知识按结构关联，不按名字

Template 的 `refines` 字段指向一个**事务模式**，不指向某个具体 kernel。模式是带参数的描述，例如：

| 模式 | 层 | 参数示例 |
| --- | --- | --- |
| reduce | 1 | 归约维；合并算子的性质：可结合、可交换、是否允许用修正因子重新缩放 |
| contract | 1 | 收缩维；参与收缩的张量 |
| map | 1 | 逐元素函数 |
| store | 2 | 值的大小；生命周期 |
| transfer | 2–3 | 源与目的存储层级；大小；对齐 |
| sync | 3 | 生产者与消费者的关系 |
| access | 5 | 存储体、端口、队列 |

Template 的 Γ 用模式参数写适用条件。例如在线归约 Template：

> refines = reduce，Γ = "合并算子可结合，且可以通过修正因子重新缩放"

于是它同时匹配 softmax、logsumexp、attention 的分母、Welford 方差。FlashAttention 只是"用到它的一条组合链"，是证据，不拥有这个思想。

**模式表是开放的。** 遇到现有模式描述不了的事务，先记为 `other` 并附上说明，覆盖页统计 `other` 的数量。同类 `other` 出现几次之后，加一个新模式。这是数据变更，不需要改代码。

### 2.3 例子：论文中 GEMM 的五步

| 步骤 | refines → produces | O | 主要变量 | 义务 |
| --- | --- | --- | --- | --- |
| 1 归约划分 | reduce → 分组部分和＋合并 | 归约分组 | 每个 k 分到哪组 | 每个乘积恰好贡献一次 |
| 2 物理存储 | store（逻辑值）→ 缓冲占用 | 缓冲 | 缓冲分配、共享缓冲的值的先后 | 值在最后一次读取前不被覆盖 |
| 3 异步传输 | transfer（原子）→ 发出＋完成 | 一次传输 | 发出与完成时间；传输方式（软件、指令、控制器） | 读取发生在传输完成之后 |
| 4 双缓冲 | 单缓冲 → S 个轮转槽 | 槽 | S、P、β | 读到正确的一代：P ≤ S − 2 + β |
| 5 共享资源 | 访问 → 对存储体、端口、队列的请求 | 请求绑定 | 绑定、队列深度 | 无冲突、无死锁、有进展 |

在 GB10 上，第 4、5 层的硬件不能改，第 5 步中的芯片变量以固定的硬件契约出现。

## 3. 组合链与可执行族

### 3.1 组合链

组合链是一个有序列表，每一项是一个 Template 实例：

```
- template: <Template ID>@<版本>
  bindings: {Template 的变量名: 族变量名或常量}
  applies_to: 这一步细化的是哪个具体事务（例如"沿 K 的归约"、"A 从 HBM 到 smem 的搬运"）
  code_regions: [生成器代码中的标记名]
```

一条链可以有分支。同一层上的几个 Template 同时作用于不同对象时（例如 A 和 B 各一次异步传输），它们共享芯片变量、边界变量和接口事件。

### 3.2 可执行族

可执行族 = 组合链 ＋ 生成器代码 ＋ 族层面的补充：

- **生成器**：给定族变量的一组取值，生成 kernel 源码。第一阶段的后端是 TileLang 和 CUDA C++（选择理由见 §3.4）。
- **代码标记**：生成器代码中用 `# kta:step <名字> begin` 和 `# kta:step <名字> end` 标出每一步对应的代码区域。gate 检查每个链项都有对应的标记。
- **胶合约束**：族特有的、不属于任何一步的约束。必须尽量少，每条都写明为什么不能归入某一步。
- **分发规则**：运行时变量的分桶。
- **边界形状**。

### 3.3 族的 formulation 由各步拼成

求解器面对的模型，按论文第 5.2 节的方式组装：

- 每个链项贡献一块：它的变量（经绑定后成为族变量）、约束 C、成本项 Ĵ；
- 再加上族的胶合约束；
- 成本按硬件单元合并：同一单元的工作量相加，然后取各单元时间的最大值，加上不能重叠的项。

所以 **formulation 是组合的**：换掉链中的一步，只需替换它那一块。

### 3.4 代码层面的组合：现在由 agent 完成，以后逐步自动化

把每一步实现为共享程序表示上的一次自动变换，是最理想的组合方式，但这等于先写一个编译器。第一阶段采用折中：

- **现在**：生成器由 worker 编写。它从相邻族的生成器和各步的参考代码片段出发，写出新的生成器，并用代码标记标出每一步。formulation 的组合由系统自动完成，代码的组合由 agent 完成。
- **以后**：覆盖页统计每个 Template 在多少个族中出现过。出现次数多、代码形式稳定的步骤，再把它做成自动变换。是否需要、先做哪些，由数据决定。

后端先选 TileLang 和 CUDA C++：本仓库已在 GB10 上用 TileLang 跑通十类 kernel 的调优；CUDA C++ 能表达任何东西。CuTe DSL 和 MLIR 方案在 M0 探测 sm_121 支持之后再评估。

## 4. 复用：迭代一系列 kernel 时增量复用

新 case 到来时：

1. **找最近的链**：按 workload 签名和所含模式，检索已有的族和参考实现的链。
2. **逐步检查适用范围**：对链中每一步，在新情境下求值它的 Γ。
   - 成立 → 保留；它的测试结论和证明随之复用，除非依赖的前提变了。
   - 不成立 → 标出。
3. **只处理标出的步骤**：换一个 alternative_of 的 Template，或者调整绑定，或者发现缺口（新 Template）。
4. 生成新版本的族：父版本＋变化的步骤。生成器代码也只改对应标记内的区域。
5. 求解、检查、测量。

**摊销指标**：每个新族中，复用的链项占全部链项的比例。

## 5. 检索

- **Template 和族由编排器确定性地检索**：
  1. 硬过滤：模式匹配；Γ 在当前情境下成立；硬件能力满足。
  2. 按证据排序：在相似情境下的表现、复用次数、保证等级。
  3. 给 agent 看的是卡片：每张不超过五行。
- **按诊断检索**：求解后，与下界的差距分解到硬件单元。用"瓶颈单元 → 涉及该单元的事务模式 → 细化这些模式、且 Γ 成立的 Template"作为检索路径。另外计算差集：相似参考实现的链里有、当前链里没有的步骤。
- **族概览**：每个算子族一页，由工具生成：有哪些族、各自的链、强项与弱项、已知缺口。

## 6. 保证等级：检查义务后移

每个 Template 和每个族都有一个**保证等级**，由工具根据证据设定：

| 等级 | 含义 |
| --- | --- |
| declared | 字段完整，义务已列出，尚未检查 |
| tested | 至少一个包含它的族，通过了空间验证（50 §4）：每条结构路径都在边界形状上测过 |
| bounded | 在有限实例上做了穷举检查，或做了有界的形式检查 |
| proved | 义务已被证明（K1–K3） |

第一阶段的要求只到 **tested**：靠测试和实测保证可用。形式化证明在积累和迭代中逐步补上。前端显示各等级的分布，以及哪些 Template 的义务还没有检查。

**declared 等级的 Template 可以使用，但它的结果在报告中单独标注。**

## 依据与待核实

- 模式表的初始内容只是起点，覆盖性靠 §2.2 的 `other` 统计和参考实现重建来检验（21、24）。
- 代码层面的组合先由 agent 完成，这是为了尽快可用而做的折中。若 agent 写生成器成为主要成本，就提前做自动变换。
- 链中有分支时，标记和绑定的写法在 WP 实施中可能需要调整。
