# 30 前端与监督

前端只有三个用途：

- **观察**：系统正在做什么，做得怎样；
- **理解**：每个结果为什么成立，系统是怎样一步步变好的；
- **介入**：在需要你的地方做决定，在出问题时叫停。

## 1. 页面

每页都回答一个问题。页面上的每个数字和结论，都能点开对应的原始记录。

| 页面 | 回答的问题 | 展示 | 可做的操作 |
| --- | --- | --- | --- |
| **待处理** | 现在有什么需要我？ | 需要你决定或审查的事项，按紧急程度排序；每项附系统的建议 | 批准、驳回、附说明重试、修改、忽略 |
| **运行中** | 系统此刻在做什么？ | 正在运行的循环、任务、agent；GPU 队列和安静租约；worker 健康；今日花费 | 暂停或恢复全部；取消任务；调整优先级 |
| **流水图** | 各部分按什么顺序、什么时候并行，每段花了多久？ | 见 §1.2 | 点击任意一段跳到对应任务或记录；从任务色块直接取消 |
| **Case** | 这个问题解决得怎样？ | 下界、各参照、当前最好结果、%下界；按形状桶的结果；**迭代时间线**：每一轮求解、每个任务、每次驳回及原因 | 发起新一轮；调整预算；把结果标记为可疑 |
| **结果详情** | 这个结果为什么可信？ | 证据链：Template 版本 → assignment → 预测 → 编译反馈与 SASS 检查 → 正确性检查 → 实测 → 与下界的差距分解 | 驳回（必须写理由）；要求重新验证 |
| **任务详情** | 这个 agent 做了什么？ | 任务卡、TASK.md 全文、`kta` 调用列表（实时）、agent 内部事件（从会话文件解析，按需展开）、时间构成、token、交付说明、工作区 diff、检查结果、驳回原因 | 取消；附说明重试；查看事件流 |
| **池** | 系统现在知道什么？ | Pattern 表；Template 及其契约、来源、保证等级；Family 及其组合链和版本差异；Reference 的重建链；Gap 列表；快照历史 | 标记可疑；废弃（必须写理由）；发起学习某个参考实现 |
| **覆盖** | 我们发现得够不够？哪里是盲区？ | 见 §1.1 | 从任一缺口发起学习任务；调整学习待办的优先级 |
| **模型** | 性能模型可信吗？ | 预测对实测的散点图；按硬件单元的残差；top-k 召回随时间的变化；按 Template 分组 | 发起诊断任务 |
| **实验** | 实验进行到哪里，结论是什么？ | 协议、各臂进度、结果表、成本曲线、摊销曲线 | 批准协议（冻结）；开始或暂停批次 |
| **改进** | 系统在变好吗？ | 每批次的归因统计；改进报告；改进前后的对比 | 批准系统代码层面的改进项 |

### 1.1 覆盖页

全集未知，所以覆盖页同时展示三个方向的估计（方法见 [21 §2](21-knowledge-admission-coverage.md)）。页面顶部始终写明抽样范围，例如"来源：公开 LLM 推理 kernel，共 37 个"。

| 图 | 横轴 / 纵轴 | 读法 |
| --- | --- | --- |
| 发现曲线 | 已拆解来源数 / 累计不同 Template 数；多次随机重排的均值和区间；叠加 Chao1 估计的总数及区间 | 曲线变平、与估计总数接近，说明在这类来源上接近饱和 |
| 覆盖率趋势 | 时间 / Good–Turing 样本覆盖率，以及"新参考实现无需扩展即可表达"的实测比例 | 两条线应该接近；差得远时，说明估计的前提不成立 |
| 指令族覆盖 | 每个指令族一行：我们能否产生、SOTA 是否用到 | 红色行 = SOTA 用到、我们产生不了 |
| 硬件特性 × 模式 | 网格；格内为 Template 数及其保证等级 | 空格是可能的盲区 |
| 结构自身 | 模式表中 other 的数量；未匹配事务按种类统计；保证等级分布；自动化的步骤数 | 见 21 §2.4 |
| 输入空间热力图 | 每类 kernel 一张，例如 GEMM 在 (M, N) 上，颜色为 %下界 | 颜色浅的区域是池子的薄弱处 |
| 差距解释率 | 每个 case 一条：已解释部分和未解释部分 | 未解释部分大的 case，优先学习 |
| 参考实现覆盖矩阵 | 参考实现 × 状态 | 卡在 Gap 的条目可以点开看缺什么 |
| 学习待办 | 按缺口排序的列表（21 §3） | 能看到系统下一步打算学什么、为什么 |

所有图都可以按快照切换。这样能看到空间是怎样一步步扩大的。

### 1.2 流水图

```
时间 →            10:00        10:05        10:10        10:15
process:solve     ■judging■    ■retrieving■                 ■solving■
agent:1               ┃T1 gemm_bf16 ─────────────────────────┃
                      ┃▒思考▒│build│▒思考▒│check│▒▒思考▒▒│submit
agent:2           ┃T2 flashinfer_decode ───────────────────────────────
worker:spark:cpu      ▓nvcc▓ ▓nvcc▓▓nvcc▓        ▓nvcc▓
gpu:spark         ░排队░█measure█ ███measure███  █check█   ← 独占租约
human                                  ◆批准协议
```

- 每一行是一条泳道：各个进程、每个 agent 槽位、各主机的执行池、GPU、你自己。
- 每个色块是一段工作（span），颜色表示种类；排队、等锁用浅色，真正干活用深色。
- 点开一个任务，能看到 agent 在里面"思考"和"调用工具"交替的过程，以及每次工具调用花了多久。
- 顶部给出这个时间窗内各泳道的利用率，例如"GPU 忙碌 12%，agent 思考占任务时间的 81%"。这正好回答"时间花在哪里、瓶颈在哪里"。
- 对一个 Case 或一次实验运行，可以显示关键路径：哪些段串起来决定了总时长。
- 实时模式下跟随当前时间滚动；也可以回看任意历史时间窗。

## 2. 什么会进入"待处理"

| 触发条件 | 为什么需要你 | 默认建议 |
| --- | --- | --- |
| 任务超过重试上限 | agent 做不下去了 | 系统附上最后一次驳回原因 |
| Case 迭代达到上限仍未完成 | 可能需要人的判断 | 列出 Gap |
| 结果大幅超过最强参照（默认超过 1.3 倍），或超过下界的 95% | 有可能是测量或检查出了问题 | 要求重新验证 |
| 同一检查在不同任务中反复失败（≥3 次） | 检查器可能有问题，也可能是系统性缺陷 | 附上失败样例 |
| 模型误差连续偏大 | 模型可能缺少关键因素 | 发起诊断 |
| 检查器崩溃，或 GPU、worker 不可用 | 基础设施问题 | 附上错误信息 |
| 预算用到 80% | 是否追加 | 附上花费构成 |
| 实验协议待批准 | 协议一旦冻结就不能改 | 附协议全文 |
| 系统代码层面的改进项 | 需要施工 agent 改代码 | 附改进报告 |
| 新 Template 或新模式会影响多个已有族 | 影响面大 | 列出受影响的族 |

上表中的阈值都是先填的数值，以后可以在设置里调整。

## 3. 介入操作

所有操作都写成 HumanAction 记录，包括你是谁、什么时间、对什么对象、理由。驳回、废弃、调整预算这三类操作必须写理由。

| 操作 | 作用 | 产生的记录 |
| --- | --- | --- |
| 暂停或恢复（全局、循环、任务） | 停止领取新任务；正在运行的任务可以选择继续或终止 | HumanAction |
| 取消任务 | 立即终止 agent 进程 | HumanAction、StatusChange |
| 附说明重试 | 你的说明会写进下一次的 TASK.md | HumanAction、新任务 |
| 调整预算或优先级 | 对之后的调度生效 | HumanAction |
| 发起任务 | 从任务类型中选择一种，填写目标和输入 | TaskCard |
| 驳回结果或知识 | 状态改为"被驳回"，依赖它的结论标记为过期 | StatusChange（actor 为人） |
| 标记可疑 | 触发重新验证，不改变状态 | HumanAction、重验任务 |
| 批准协议 | 冻结实验协议，实验可以开始 | Protocol、StatusChange |
| 批准改进项 | 交给施工 agent | HumanAction |
| 编辑 Template | 你手写的修改作为新版本，标注作者是人 | Template |

## 4. 实时性与访问

- 前端通过 SSE 接收实时更新：任务状态、工具调用、日志。
- 后端服务运行在控制面所在机器上，只监听本机端口。控制面在本机时直接访问；在其他机器时经 SSH 隧道访问。
- 只有一个用户，不做登录。不暴露到公网。

## 5. 后端 API

前端和 `kta` 命令都使用同一套 API：

- **读接口**：记录查询、证据链、搜索、循环和任务状态、统计数据、SSE 事件流。
- **操作接口**：上表中的每个操作各对应一个接口，统一写 HumanAction 记录。

## 6. 第一阶段不做

- 多用户和权限管理。
- 在前端直接编辑代码（编辑 Template 走"导出 → 修改 → 提交"的流程）。
- 移动端适配。
