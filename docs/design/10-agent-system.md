# 10 Agent 系统：怎样构造、怎样运行

本文讲**运行时 agent**：KTA 运行时调用的 LLM agent。编写 KTA 代码的施工 agent 见 [60](60-build-and-acceptance.md)。

## 1. 总体结构

```
            ┌──────────── 编排器（确定性代码）────────────┐
 你 ──前端──►│ 求解循环   扩展循环   改进循环              │
            │      │          │          │                │
            │      ▼          ▼          ▼                │
            │  ┌────────── 任务队列 ──────────┐            │
            │  │ 确定性任务         agent 任务 │            │
            │  └────┬───────────────┬────────┘            │
            └───────┼───────────────┼────────────────────┘
                    ▼               ▼
               执行器(编译/       agent 运行器 ──► LLM CLI 进程
               检查/测量)              │          （在隔离工作区内）
                    │                 │ 只能通过 kta 工具
                    ▼                 ▼
                         存储（记录 + 产物）
```

图中的编排器实际由几个相互独立的常驻进程组成（求解、学习、校准、维护、实验、汇总）。它们怎样分工、怎样分配时间和资源、怎样加锁，见 [11](11-processes-resources-concurrency.md)。本文只讲单个任务怎样执行。

核心原则：

1. **流程由确定性代码驱动。** 编排器决定下一步做什么，LLM 不决定流程。
2. **只在需要创造性工作时调用 LLM**，例如写生成器、分析参考实现、诊断模型误差。其余步骤（求解、编译、检查、测量、比较）都是确定性代码。
3. **agent 的产出必须经过检查才生效。** agent 只能提交"提议"；检查通过后，由编排器推进状态。
4. **agent 能接触的东西有边界。** 合同、检查器、隐藏形状、baseline、存储，agent 都不能写；GPU 只能通过执行器使用。

为什么这样设计：编排交给 LLM，要用多倍的 token 换取不稳定的收益，而且出了问题难以定位。流程固定在代码里，每一步都有记录，失败可以归因。

## 2. 编排器：三个循环

每个循环是一个状态机，状态保存在存储中。进程重启后，从保存的状态继续。求解循环由求解进程运行，扩展循环由学习进程运行，改进循环由汇总进程运行（见 11 §1）。

### 2.1 求解循环（每个 Case 一个实例）

| 状态 | 做什么 | 下一状态 |
| --- | --- | --- |
| `new` | 规范化 Case，固定 baseline 集 | `bounded` |
| `bounded` | 按形状桶计算理论下界 | `retrieving` |
| `retrieving` | 在当前池快照中检索合法 Template | 找到 → `solving`；没找到 → 创建任务 T1，进入 `waiting` |
| `solving` | 用编译前模型选出候选短名单（默认 64 个） | `building` |
| `building` | 并行编译，读编译反馈，检查 SASS 特征，用编译后模型重排，取前 k 个（默认 8 个） | `checking` |
| `checking` | 对前 k 个做完整正确性检查 | `measuring` |
| `measuring` | 按测量协议实测；必要时补测 baseline | `judging` |
| `judging` | 与下界和参照比较，按硬件单元分解差距，然后判定 | 见下 |

`judging` 的判定规则，按顺序匹配：

1. 有正确性失败 → 创建任务 T6（修 Template）→ `waiting`
2. 前 k 个的预测与实测排序严重不符，或误差超过阈值 → 创建任务 T4（诊断模型）→ `waiting`
3. 达到判据（不低于最强参照，或与下界的差距已被解释）→ `accepted`
4. 差距无法解释 → 创建扩展任务（T2 学习参考实现，或 T1 扩展 Template）→ `waiting`

`waiting` 中的任务被接受后，循环回到产生任务的那个状态。

每个 Case 默认最多迭代 5 轮，到上限仍未 `accepted`，就升级给你处理（进入待处理队列）。

### 2.2 扩展循环（每个 Reference 一个实例）

| 状态 | 做什么 |
| --- | --- |
| `frozen` | 来源冻结到 commit 或 hash；在容器中构建 |
| `measured` | 按我们的协议检查和实测，得到参考点 |
| `analyzing` | 任务 T2：worker 按 24 和 skill `decompose-kernel` 把参考实现拆成组合链，逐步匹配已有 Template |
| `reconstructed` 或 `gap` | 全部步骤匹配 → 用某个族生成 kernel 并复现性能；有未匹配的步骤 → 写 Gap，创建 T3 提取新 Template（必要时 T1 扩展族），完成后回到 `analyzing` |
| `reproduced` | 复现误差在 ε 以内且通过检查 |
| `ablated` | 逐个关闭链中可以关闭的步骤并实测（确定性任务），结果作为校准数据 |
| `covered` | 更新覆盖状态 |

### 2.3 改进循环（每批次一次，或由你手动触发）

1. 汇总这一批的 Gap 和 `judging` 结果，按六类归因统计次数和损失：空间、模型、意图与 SASS 不符、验证、流程、粒度。
2. 生成一份改进报告（一条记录）以及建议的改进项。
3. 知识层面的改进（补 Template、校准模型）自动创建运行时任务。
4. 系统代码层面的改进（工具、检查器、流程）进入你的待处理队列，由你批准后交给施工 agent。
5. 用开发集 case 验证改进效果，留出集不参与。

## 3. 任务

### 3.1 任务类型

| 类型 | 谁执行 | 目的 | 必须交付 | 完成检查 |
| --- | --- | --- | --- | --- |
| 编译、检查、测量、profile、消融 | 执行器 | 确定性工作 | 对应记录 | 执行成功 |
| T1 构造或扩展族 | worker | 新建可执行族，或出新版本：组合链＋生成器 | 族（链、生成器、代码标记） | 链一致性检查和空间验证通过（见 50 §4） |
| T2 拆解参考实现 | worker | 把 Reference 拆成组合链 | Reconstruction（链、匹配率、未匹配事务、Gap） | 字段完整；匹配的步骤都引用已有 Template |
| T3 提取 Template | worker | 从来源或 Gap 中提取一个细化步骤 | Template 记录（declared），引用到来源的具体行 | 字段完整；查重通过 |
| T4 诊断模型 | worker | 解释预测误差 | 修订的成本项及证据 | 在留出点上误差下降 |
| T5 编写 microbenchmark | worker | 测一个硬件参数 | benchmark 及结果 | 重复测量一致 |
| T6 修族或 Template | worker | 修正确性失败 | 族或 Template 的新版本 | 失败的用例通过，空间验证通过 |

### 3.2 任务生命周期

```
created → queued → leased → running → submitted → checking → accepted
                                                       │
                                                       └→ rejected → queued（附驳回原因，重试次数 +1）
                                                                  └→ 超过重试上限 → escalated（进入你的待处理队列）
任意状态 → cancelled（由你取消）
running  → expired（超预算或无响应）→ 按 rejected 处理
```

- 重试上限默认 2 次。每次重试，都把上一次的驳回原因写进新的提示。
- `escalated` 的任务停在你的待处理队列里，你可以选择：附上说明后重试、修改任务、放弃。

### 3.3 任务卡

每个任务由一张任务卡定义。任务卡作为不可变记录保存：

| 字段 | 内容 |
| --- | --- |
| 类型 | T1–T6 |
| 目标 | 一句话 |
| 输入 | 相关记录的 ID（Case、Template 版本、Reference、Gap 等） |
| 完成检查 | 由哪些检查判定完成（固定，agent 不能改） |
| 预算 | 墙钟时间、GPU 秒、步骤数；token 只在适配器能实时拿到用量时生效 |
| 可用工具 | 默认是全部 `kta` 命令，可以收窄 |
| skills | 需要读的 skill 列表 |
| profile | 使用哪个 AgentProfile 版本（§4.10）：provider、模型、提示模板、上下文与循环策略 |
| 工作单元 | 所属的循环实例；同一工作单元的步骤共用一个会话（§4.2） |

## 4. agent：角色、会话、上下文与实例

### 4.1 角色只按边界划分

只有三种情况才值得划出一个单独的 agent 角色：

1. **权限边界不同**：能写的、能看的东西不同；
2. **需要独立判断**：不能共享别人的上下文，否则会继承它的盲点；
3. **并行**：这只需要同一角色多开几个实例，不产生新角色。

任务类型不同不构成理由。T1–T6 都由同一个 worker 完成，区别只在于这一步的目标和要读的 skill。

| 角色 | 划分理由 | 权限 | 实例数 |
| --- | --- | --- | --- |
| worker | 唯一的运行时角色 | 写自己的工作区；经 `kta` 读存储、提交交付物 | 等于并行度（§4.5） |
| 审计（可选） | 只读，独立于 worker 的上下文 | 读记录和来源；只能写审计报告 | 抽样运行，默认不开 |

编排者由确定性代码担任，不用 LLM。正确性由检查器和隐藏测试保证，不另设"验证 agent"。施工期的角色见 [60](60-build-and-acceptance.md)。

### 4.2 会话：一个工作单元一个会话

**工作单元**指一个循环实例：一个 Case 的求解循环，或一个参考实现的扩展循环。

- 一个工作单元对应一个 agent 会话。循环中的多个 agent 步骤（写 Template、被驳回后修改、诊断模型）都在同一会话中继续，用 provider 的会话恢复功能。
- 每一步只发一条增量消息，例如"完成检查未通过：隐藏形状 (1, 4097) 最大误差 0.31"。不重发整套上下文。
- **状态写在磁盘上，会话可以丢弃。** worker 在工作区持续更新 `NOTES.md`：当前目标、做了什么、试过什么、为什么失败、下一步打算。编排器在以下情况结束旧会话、开新会话，新会话从 `NOTES.md` 和记录接着做：
  - 上下文超过阈值（默认为模型窗口的 60%）；
  - 同一项检查连续两次因相同原因失败，换一个"新视角"；
  - 工作单元结束；
  - 会话异常。
- 实验中，每次运行都用全新会话，各臂、各次重复之间不共享任何历史。
- 会话作为记录保存：provider 会话句柄、所属工作单元、会话文件位置、状态（活跃、暂停、关闭）。会话文件按工作单元持久保存，结束时存档。

### 4.3 一次 agent 步骤的过程

1. 编排器为工作单元创建一个任务（任务卡见 §3.3），放入队列。
2. 运行器领取任务，取得租约（默认 30 分钟，运行期间定期续约）。
3. 工作区 `work/<工作单元 ID>/` 在整个工作单元内保留：`inputs/` 放复制进来的源码，`out/` 放交付物，另有 `NOTES.md`。工作区用 git 管理，每一步结束时提交一次，方便看 diff。
4. 运行器决定恢复已有会话还是开新会话（§4.2），然后以 `kta-agent` 用户的身份启动 CLI。环境变量中放入任务令牌，`kta` 用它识别当前任务、记录调用并检查权限。
5. 新会话收到完整的提示（§4.4）；恢复的会话只收到这一步的增量消息。
6. 运行器保存 CLI 的输出和会话文件，记录会话起止；`kta` 实时记录每次工具调用。agent 内部的思考与工具事件，需要时由会话解析器从会话文件中解析（11、30 的流水图据此展开）。
7. worker 执行 `kta submit` → 任务进入 `checking` → `accepted` 或 `rejected`。
8. 工作单元结束时，工作区打包存档，然后删除。

### 4.4 上下文：少给，按需取

新会话的提示由三部分组成：

| 部分 | 内容 | 要求 |
| --- | --- | --- |
| 固定前缀 | `use-kta` skill 的要点、不能做的事、交付规则 | 所有会话字节级相同，以便命中提示缓存 |
| 步骤头 | 目标、完成检查、剩余预算、相关记录的 ID（最多 5 条摘要）、建议读的 skills | 一页以内 |
| 按需获取 | 知识经 `kta query`、`kta show` 获取；skill 由 worker 自己决定读不读 | 不预先塞入 |

其他节省 token 的规则：

- **工具输出默认精简。** 编译日志、ncu 报告、检查结果等大输出，先由确定性代码压缩成摘要和 ID；需要原文时加 `--full`。
- **重复工作不交给 agent。** worker 只写 Template、合法条件和成本项；候选的编译、检查、测量由编排器批量完成，worker 不需要逐个手动运行工具。
- **大型源码不整体阅读。** 参考实现的源码通过带索引的检索工具（`kta src`）按符号和关键词查找。
- **驳回时只给差异。** 重试消息只包含不通过的项和相关的 ID，不重复已经说过的内容。

提示模板和固定前缀保存在仓库中，有版本，其 hash 写入运行记录。

### 4.5 同时运行多少个实例

- 实例数取以下几项中的最小值：预算允许的消耗速度、provider 的速率限制、当前可做的独立工作单元数、GPU 队列不拥堵时能承受的量。
- 已有数据显示，agent 时间约 52 分钟，GPU 时间约 54 秒，GPU 多数时间空闲。所以增加实例能提高吞吐，直到 GPU 排队或预算成为瓶颈。
- 默认从 2 个起，上限 4 个。GPU 排队时间变长，或预算消耗快于计划时减少；有积压且 GPU 空闲时增加。
- 同一个工作单元内，不让多个实例并行。

### 4.6 provider 适配

运行器只依赖一个适配器接口：

```
start(prompt, workspace, env, limits) -> 会话句柄, 事件流
resume(会话句柄, message, limits)     -> 事件流
```

第一阶段只实现并使用 Codex（`codex exec`，JSON 事件输出，`resume` 恢复会话）。Codex 自动读取工作目录中的 `AGENTS.md`，所以 worker 的固定前缀写在工作区的 `AGENTS.md`。Claude Code 适配器保留接口，暂不启用，以后需要时再实现。不支持恢复会话的 provider，每一步都开新会话，从 `NOTES.md` 接续。其他模型（如 DeepSeek）需要一个能在无头模式下执行 shell 工具的 agent CLI，接入前先探测。provider 不报告 token 时，按估算记录并标明"估算"。

### 4.7 隔离与权限

| 资源 | worker 的权限 | 怎样强制 |
| --- | --- | --- |
| 工作区 | 读写 | 文件权限 |
| 存储（记录、产物） | 只能经 `kta` 读取和提交 | `kta-agent` 用户对数据目录没有写权限 |
| 合同、检查器、隐藏形状集、baseline | 不可见或只读 | 不放进工作区；`kta check` 只返回结论和不通过的样例，不返回隐藏形状本身 |
| GPU | 只能经 `kta run`、`kta measure` | `kta-agent` 用户没有 GPU 设备权限 |
| 网络 | 只允许访问 LLM API | 第一阶段先不强制，只记录；需要时加防火墙规则 |

### 4.8 预算与取消

- 墙钟时间：到时终止进程树，任务记为 `expired`。排队时间不计入，但总墙钟时间达到预算 3 倍时强制终止（见 11 §3.3）。
- token：只在适配器能实时拿到用量时设上限；订阅方式的 CLI 通常不设。
- GPU 秒：由执行器累计，超出后拒绝新的 GPU 作业。
- 无响应：CLI 输出和会话文件连续 10 分钟没有变化，视为卡住，终止。
- 你在前端取消任务时，立即终止进程树。

### 4.9 并发、预算层级与锁

见 [11](11-processes-resources-concurrency.md)。agent 进程从不直接持有锁，锁由编排器和执行器代为持有。

### 4.10 受控的 agent 设置

agent 的行为由三样东西决定：给它什么上下文、它按什么策略循环、它能用哪些工具。这三样如果不受控，会带来三个问题：结果无法复现；实验各臂之间不公平；提示被零散修改后，行为悄悄漂移。

所以三样东西全部写进一个有版本的 **AgentProfile**，除此之外的任何东西都不得影响 agent。精确定义见 spec/modules/agents.md。

**profile 包含：**

- provider、CLI 版本、模型、推理强度、CLI 参数（沙箱、审批、关闭 web search 和 MCP）；
- 隔离的 CLI 配置目录：每次运行都指向它，用户级的配置、AGENTS.md 和 skills 不会被读到；
- 提示模板：固定前缀、各任务类型的步骤头、增量消息；
- 各任务类型可用的 skills 和 `kta` 子命令；
- 上下文策略：检索卡片最多几张、每张几行、工具输出截断长度、步骤头长度上限；
- 循环策略：重试次数、什么情况换新会话、无响应超时、各任务类型的预算。

**提示里告诉 agent 什么：**

| 部分 | 内容 |
| --- | --- |
| 固定前缀（worker 工作区的 AGENTS.md，约一页） | 你是谁、做什么（一两句）；工作方式：先读 TASK.md 和 NOTES.md，随时更新 NOTES.md，用 `kta` 获取信息和执行，自查后 `kta submit`；硬规则：只在工作区写文件，GPU 和存储只经 `kta`，不得修改或绕过检查，不得返回假结果，简化必须申报，不联网检索，不读工作区外的文件；交付说明的格式；可用 skills 的名称和一句话说明 |
| 步骤头（TASK.md，一页以内） | 目标；输入记录的 ID 和卡片（最多 5 张）；完成检查原文；预算与剩余；建议读的 skills；上一次驳回的原因（如有） |
| 增量消息 | 驳回：不通过的检查项原文和相关 ID；预算用到 80% 的提醒；你的说明（原文，标明来自你）；换新会话时提示"先读 NOTES.md" |

**提示里不告诉 agent 什么：**

- 隐藏形状、检查器的内部实现、随机种子；
- 实验中其他运行或其他臂的结果；
- 上一个会话的完整记录（只有 agent 自己写的 NOTES.md）；
- 整个池子或长文档（需要时自己用 `kta` 取）。

**谁能改：** profile 只能出新版本；切换当前版本需要你批准。agent 不能修改自己的 profile、提示模板或 skills。改进进程可以提出新版本，并在开发集上与当前版本对比后交给你批准。实验期间 profile 固定不变。

**怎样确认 agent 照做：** 每次运行都有上下文清单（实际加载了哪些文件、各自的 hash），以及合规统计（越权尝试、未允许的命令、工作区外写入）。同类违规反复出现时，进入待处理队列。

## 5. 工具：`kta` 命令

agent 和人都使用同一套命令。每次调用都产生记录，并关联到当前任务。

| 命令 | 作用 | 产生的记录 |
| --- | --- | --- |
| `kta show <id>` | 查看一条记录的详细内容 | — |
| `kta query pool --case <id>` | 检索适用的族、Template、Reference，返回摘要 | — |
| `kta query tmpl <模式/标签/关键词>` | 按模式、标签和全文检索 Template | — |
| `kta query chain --near <case 或 family>` | 检索最近的组合链（增量复用的起点，22 §4） | — |
| `kta why <id>` | 列出一个结论的证据链 | — |
| `kta instantiate <template> <assignment>` | 生成源码 | — |
| `kta build <source>` | 编译，返回编译反馈（寄存器、spill、smem） | Build |
| `kta sass <build>` | 指令统计，以及与预期 SASS 特征的比对 | — |
| `kta check <build> --contract <id>` | 数值检查、sanitizer、反作弊检查 | Check |
| `kta run <build>` | 快速运行一次，不进入正式结果 | — |
| `kta measure <build>` | 按协议正式测量 | Measurement |
| `kta profile <build>` | Nsight Compute profile，返回结构化指标 | Profile |
| `kta bound <case>` | 计算理论下界 | Bound |
| `kta solve <template> <case>` | 求解，返回候选和预测 | Prediction |
| `kta validate-template <file>` | 校验 Template 记录的字段、表达式语法、与已有 Template 的关系、查重 | Check |
| `kta validate-family <dir>` | 校验族：链一致性（每个链项有绑定和代码标记、约束表达式可求值）、空间验证 | Check |
| `kta note <text>` | 写一条备注，附在任务记录上 | Note |
| `kta submit` | 提交 `out/` 中的交付物和交付说明 | Submission |

## 6. 工具、skills 与池知识

agent 工作时用到三类东西，必须分开：

|  | 工具（`kta` 命令） | skills | 池知识 |
| --- | --- | --- | --- |
| 是什么 | 确定性的动作 | 怎样完成某一类任务的方法 | 关于某种硬件、某类 kernel 的设计知识 |
| 例子 | `kta build`、`kta query` | 怎样写族和代码标记；怎样把参考实现拆成组合链；怎样写 Template 契约；怎样写 microbenchmark；怎样诊断模型误差；怎样检索知识 | Pattern、Template、Family、Reference、HwFact |
| 存放 | 代码 | 仓库 `src/kta/agents/skills/`，随代码一起版本化；运行时复制到 worker 工作区的 `.agents/skills/` | 存储，按快照固定 |
| 怎样交给 agent | PATH 上的命令 | 任务卡列出要读的 skills | 经 `kta query`、`kta show` 检索；文字知识条件下渲染成文件放进工作区 |
| 留下的记录 | 每次调用都有记录 | skill 版本 hash 写入 AgentRun | 被检索到的记录 ID 写入调用日志 |
| 换 GPU 或换 kernel 类型时 | 不变 | 基本不变 | 变 |
| 在实验中 | 各臂相同 | **各臂相同** | 各臂不同，正是被比较的变量 |

判断一项内容属于哪一类：

1. 会执行动作、产生记录 → 工具。
2. 换一块 GPU、换一类 kernel 就要改 → 池知识。
3. 说明怎样完成一类任务、怎样使用系统 → skill。

**为什么必须严格分开。** 实验比较的是不同的知识条件，而 skills 在各臂相同。如果某个 skill 里写进了领域知识（例如"decode 应该做 split-KV"），从零构造那一臂就提前拿到了这条知识，比较就失去意义。所以 skill 只写方法，不写具体硬件或 kernel 的设计结论。独立验收的清单中包含这一项。

**检索与 skill 的关系。** 检索动作是工具（`kta query`），因为要记录 agent 查了什么、看到了什么。"怎样检索、怎样使用检索结果"写成 skill（`find-knowledge`）。skill 可以包装检索方法，但检索动作本身仍然经过工具，留下记录。

**第一批运行时 skills：**

| skill | 用于 |
| --- | --- |
| `use-kta` | 所有任务：工具用法、交付规则、不能做的事 |
| `find-knowledge` | 所有任务：怎样检索、怎样判断检索结果是否适用 |
| `write-family` | T1、T6 |
| `decompose-kernel` | T2 |
| `write-template` | T3 |
| `diagnose-model` | T4 |
| `write-microbench` | T5 |

运行时 agent 的 skills 源文件放在 `src/kta/agents/skills/`，启动 worker 时安装到它工作区的 `.agents/skills/`；施工 agent 的 skills 放在本仓库的 `.agents/skills/`。两者分开存放，互不混用，都不安装到用户级目录。

## 7. 交付与检查

- `kta submit` 要求交付说明包含：做了什么、用了哪些简化或 fixture（没有就写"无"）、有哪些已知问题。
- 编排器按任务卡上的完成检查逐项执行，全部通过才算 `accepted`。
- 驳回时，原因写成具体的不通过项，例如："隐藏形状 (1, 4097) 上最大误差 0.31，超过容差"。
- 检查器出错（检查器自身崩溃）和 agent 的交付不通过是两回事：前者把任务挂起并通知你，不计入 agent 的重试次数。

## 8. 记录了什么

每次 agent 运行都记录：

- 任务卡 ID，提示模板的 hash，模型和 provider 的版本；
- CLI 输出和会话文件（按工作单元持久保存并存档，不含凭据）；
- 每次 `kta` 调用：命令、参数、耗时、结果记录 ID；
- 时间构成：`kta` 工具耗时、排队耗时，以及其余时间（主要是模型耗时）；
- token 用量：会话文件中带有时由解析器记下，不要求；费用由你的其他工具分析；
- 交付物、交付说明、检查结果、最终状态。

不要求、也不保存模型的隐藏思维链。

## 9. 失败处理

| 失败 | 判定方式 | 处理 |
| --- | --- | --- |
| agent 交付不通过 | 完成检查失败 | 驳回后重试，超过上限则升级 |
| agent 卡住 | 10 分钟无事件 | 终止，按驳回处理 |
| 超预算 | 运行器计量 | 终止，记为 `expired` |
| 工具或执行器故障 | 执行器报错 | 归为基础设施错误，工具自动重试；不计入 agent 的重试次数 |
| GPU 挂起 | 作业超时，且 GPU 无响应 | 标记该 worker 不可用，通知你 |
| 检查器崩溃 | 检查器异常退出 | 挂起任务，通知你 |
| 同一检查在不同任务中反复失败 | 统计到同类失败 ≥3 次 | 进入待处理队列：可能是检查器有问题，也可能是系统性缺陷 |

## 10. 例子：一个新的 GQA decode case

1. 你在前端创建 Case（或由实验批次创建）。求解循环进入 `new`。
2. `bounded`：按 (batch, kv_len) 分桶，计算各桶的 DRAM 带宽下界。
3. `retrieving`：池中没有支持 Hkv=8、D=128 的 decode 族，但有一条相近的 decode 链 → 创建 T1，以这条链为起点。
4. T1：worker 读到 TASK.md，看到最近的链，以及 Γ 在新情境下不成立的两步。它只替换这两步，改对应标记内的代码，用 `kta validate-family` 自查，再 `kta submit`。完成检查发现，split 路径在 extreme logits 输入下数值超限 → 驳回，原因写明 → 重试。第二次通过。
5. `solving` → `building`：64 个候选中，有 3 个声明使用 cp.async，但 SASS 里没有 LDGSTS → 标记"意图未实现"，写 Gap。
6. `measuring` → `judging`：长 KV 桶达到下界的 1.6 倍，其中只有一部分能被解释 → 创建 T2，参考实现为 FlashInfer decode（需先确认 sm_121 上可用）。
7. T2：agent 发现参考实现按每个请求的实际长度做 split 负载均衡 → 写 Gap → 创建 T1，补一个"按实际长度做 split 负载均衡"的 Template（T3）→ 族换上这一步，出新版本（T1）。
8. 回到 `solving`，长 KV 桶达到下界的 1.15 倍，剩余差距由 wave 量化和合并开销解释 → `accepted`。

你在前端能看到这个 Case 的时间线（每一轮、每个任务、每次驳回的原因），以及最终结果的证据链。以上数字仅为示意。
