# 21 知识的准入与覆盖

知识单元的定义见 [22](22-template-format-retrieval-composition.md)，图结构见 [23](23-knowledge-structure.md)。检查义务后移：第一阶段只要求经验上可用（保证等级到 tested），形式化保证和覆盖在积累中逐步可见（22 §6、本文 §2.4）。

本文回答两个问题：一条知识怎样进入池子；在不知道全集的情况下，怎样判断我们发现得够不够。

## 1. 知识怎样被记录

### 1.1 原则：记录门槛低，使用门槛分级

- **记录门槛低。** worker、导入脚本或你注意到的任何东西，只要带上来源，就可以记为"提议"。宁可多记，事后再筛。没有记下来的知识，以后就无法复用，也无法统计覆盖。
- **使用门槛分级。** 一条知识能被用在哪里，取决于它的状态：

| 状态 | 怎样达到 | 能用在哪里 |
| --- | --- | --- |
| 提议 | 字段完整，带来源 | 作为提示出现在检索结果里，标明"未验证" |
| 已复现 | 在目标硬件上有实现用到它，并通过检查 | 求解器可以使用 |
| 已校准 | 消融实验显示可测量的效果，带置信区间 | 进入成本模型 |
| 留出集验证 | 在留出 case 上，效果与预测一致 | 进入正式结论 |
| 废弃 | 被证伪，或依赖的前提失效 | 只在历史中可见 |

状态推进的规则见 [20 §2.2](20-storage-retrieval.md)：agent 只能创建"提议"，检查器推进，人可以否决。

### 1.2 各类知识的准入要求

| 类别 | 必填内容 | 推进到"已复现"的证据 |
| --- | --- | --- |
| Template（细化步骤） | 22 §2.1 的全部作者字段，其中必须有：refines 的模式；新对象 O；变量；约束；Γ；义务清单 Σ（可以只列出、暂不检查）；与已有 Template 的关系；来源（精确到文件和行，或文档章节）；最小代码示例 | 至少一个通过检查的族用到它，且 SASS 特征与声明一致 |
| Pattern（事务模式） | 所在层；种类；参数及其性质；至少两个例子 | 你确认 |
| 硬件事实 | 参数或行为；测量方法或文档出处 | 文档来源：标"有文档"；microbenchmark 重复测量一致：标"已实测"。两者冲突时，以实测为准，冲突本身也记录下来 |
| Family（可执行族） | 组合链；生成器；代码标记；胶合约束；边界形状 | 空间验证通过（50 §4） |
| Reference | 来源冻结；构建方式 | 在我们的协议下通过检查并完成实测 |
| **负面知识** | 某个做法在什么条件下没有效果或有害；证据 | 消融或实测显示无效果或负效果 |

**负面知识必须记录。** 其他 kernel agent 的一个常见浪费是：每次都重新尝试已知无效的做法。"cp.async 多级流水在这类 decode 上没有收益，因为瓶颈在 X"这类结论，同样作为知识入池，检索时一并返回。

### 1.3 去重与粒度

- 新的 Template 提议入池前，先查重：refines 同一模式、引入同类对象、变量和成本项相同的，视为疑似重复。worker 必须说明它与已有条目的区别；说不出区别的，作为已有条目的一个新来源合并。
- 去重直接影响覆盖统计：同一个步骤被记成三条，覆盖曲线就会虚高。
- 粒度规则：一个 Template 细化一种模式、引入一个对象（论文的定义）。同时改变多个事务的做法，先按实际情况记录，是否拆分由拆解中积累的例子决定（24 §5）。

### 1.4 冲突与过期

- 同一件事有两个互相矛盾的结论时，两条都保留，并生成一条冲突记录，交给校准进程用实测裁决。
- 工具链、驱动或 Target 变化后，依赖它们的"已校准"知识标为过期，由维护进程重新验证。编译器的改进可能让一个步骤的效果消失，反之亦然。

### 1.5 许可

Template 中直接复制的外部代码，记录其来源和 license。license 不允许的，只记录 Template 的契约和思路，不复制代码。

## 2. 不知道全集，怎样看覆盖

全集无法列举。但可以从三个方向逼近它，每个方向都给出一个可以测量、可以展示的量。

### 2.1 从发现过程估计：还有多少没见过

把每个来源（一个参考实现、一份文档、一篇论文）看作一次抽样，把每个 Template 看作一个"物种"。这是生态学里估计未知物种数的标准问题。

- **发现曲线**：横轴是已处理的来源数，纵轴是累计的不同 Template 数。对来源顺序随机重排多次，画出均值和区间。曲线变平，说明新来源带来的新 Template 越来越少。
- **未见 Template 数的估计**（Chao1）：S_est = S_obs ＋ f1² / (2·f2)。其中 S_obs 为已见 Template 数，f1 为只在一条重建链中出现过的 Template 数，f2 为恰好在两条中出现过的数。
- **样本覆盖率**（Good–Turing）：C ≈ 1 − f1 / n，n 为 Template 在所有重建链中出现的总次数。含义是：再拆解一个新来源，它的某一步已经在池子里的概率。
- **直接检验**：定期拿一个从未处理过的参考实现，看它能否不经扩展就被拆成已有 Template 的组合链（24）。这个比例随时间变化的曲线，是对上述估计的实测校验。

**限制：** 这种估计只覆盖"我们抽样的那类来源"。如果来源都是公开的 LLM 推理 kernel，那么结论就是"对公开 LLM 推理 kernel 所用细化步骤的覆盖率"，不能推广到所有可能的设计。展示时必须写明抽样范围。

### 2.2 从硬件出发：有限的那一侧

硬件的能力是有限的，可以列举：

- **指令族**：从 PTX ISA 文档和 microbenchmark 中列出 sm_121 支持的指令族，例如各类 MMA、异步拷贝、TMA、各级 load/store、同步、原子操作。
- **资源和单元**：各级存储、各类执行管线、同步原语。

在此基础上可以测量两种覆盖：

- **指令覆盖**：每个指令族，我们的生成器能不能产生它；SOTA 参考实现的 SASS 里有没有用到它。**SOTA 用到而我们产生不了的指令族，就是确定存在的缺口。**
- **硬件特性 × 模式网格**：每格记录"requires 这项硬件能力、refines 这种模式的 Template 有几个，各处于什么保证等级"。空格是可能的盲区，值得去找来源。

### 2.3 从结果出发：够不够用

不论全集多大，对一个具体的 case 来说，问题只是"空间够不够用"：

- **差距解释率**：每个 case 的实测时间与理论下界之间的差距中，有多少比例已被具体因素解释。解释不了的部分，就是证据表明空间或模型还缺东西。
- **输入空间上的覆盖**：对一类 kernel，在形状和 dtype 空间上画 %下界的热力图。例如 GEMM 在 (M, N, K) 上：哪些区域接近下界，哪些区域明显落后（比如 decode 时的小 M）。落后的区域就是池子的薄弱处。
- **参考实现覆盖矩阵**：每个参考实现的重建链匹配率（匹配上的步骤 ÷ 全部步骤）、未匹配的事务数、是否复现。

### 2.4 结构自身的覆盖

除了"发现得够不够"，还要看"我们的结构本身够不够用"：

- **模式表中 `other` 的数量和增长**：多，说明模式表需要扩充；
- **未匹配事务**：重建链没有解释的事务，按种类统计；
- **保证等级分布**：declared、tested、bounded、proved 各有多少 Template，哪些义务还没检查；
- **代码组合的自动化程度**：多少步骤已做成自动变换（22 §3.4）。

这些都不需要事先保证。它们在积累和迭代中被持续计算、展示；发现缺的就补上。

### 2.5 三个方向一起用

| 方向 | 回答 | 弱点 |
| --- | --- | --- |
| 发现过程 | 按当前的来源，还有多少细化步骤没见过 | 只覆盖抽样的那类来源 |
| 硬件 | 哪些硬件能力我们还没用上 | 用上了某条指令，不等于用对了 |
| 结果 | 对实际的 case，空间够不够 | 只覆盖已经测过的 case |

三个方向的结论一致时，覆盖的判断才比较可信。如果它们不一致，例如发现曲线已经平了，但差距解释率仍然很低，那么说明抽样的来源有偏，需要换一类来源。

## 3. 覆盖驱动学习

学习进程的待办列表，按覆盖缺口排序：

1. 结果方向上损失最大的缺口：未解释差距大、出现在多个 case 中的；
2. 硬件方向上 SOTA 用到而我们产生不了的指令族；
3. 硬件特性 × 模式网格中的空格；模式表中反复出现的 `other`；
4. 发现曲线上仍在快速增长的来源类别。

每次学习完成后，重新计算覆盖指标。这样，"下一步学什么"由数据决定，不靠 agent 或人的直觉。

## 依据与待核实

- Chao1 和 Good–Turing 是成熟的统计方法，但用在"细化步骤的发现"上是助手的推断。它们的前提（来源之间相互独立、同一总体）只是近似成立，需要用 §2.1 中的直接检验来校验。
- sm_121 的指令族清单需要从 PTX ISA 文档和 M0 探测中整理。
- 负面知识的检索方式（怎样在检索结果中呈现、避免误导 agent 放弃可行方向），需要在 M2 之后根据使用情况调整。
