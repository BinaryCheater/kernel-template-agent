# 00 总览

## 1. 要证明什么

用 LLM 优化 kernel 的常见做法，是每个问题都让强模型花大量 token 做一次。KTA 把 token 用在积累上：从 SOTA 实现和硬件实测中学到的设计决策，沉淀为可执行的 **Template**（设计空间）和**性能模型**。新问题主要靠检索、求解和少量实测完成，只有空间或模型不够用时，才调用 agent 扩展它们。

要证明的主结论（默认，待你确认）：

1. **摊销**：池子积累得越多，新 case 花的 token、时间和实测次数越少；弱模型借助池子，能接近强模型从零做的结果。
2. **覆盖**：池子能把一批 SOTA 参考实现表达为自己空间中的点，并复现它们的性能。

辅助结论：

- **饱和**：每加入一个参考实现，需要新增的 Template（细化步骤）越来越少。
- **预测**：性能模型能把候选排对顺序，从而减少实测次数。
- **质量**：在留出 case 上，结果对照理论下界和最强实现的位置。
- **可诊断**：结果不理想时，能定位到具体组件。

## 2. 和谁比

- **性能对照**：每个 case 都与当前能找到的最强实现比较（cuBLASLt 算法搜索、CUTLASS profiler、FlashInfer 等，按 sm_121 实际可用的为准），同时报告与**理论下界**的距离。理论下界按硬件单元计算：最少工作量除以实测峰值，取各单元中的最大值。
- **方法对照**：同一批 case，分三种知识条件运行：从零构造、文字知识（同一池子渲染成文字）、可执行 Template 池。每种条件各配一个强模型和一个弱模型。

## 3. 核心概念

| 概念 | 含义 |
| --- | --- |
| Case | 一个要优化的问题：计算语义、正确性合同、形状分布、硬件、目标函数 |
| Pattern | 事务模式：一种粗事务（归约、收缩、存储、搬运、同步……）及其参数。开放的表，描述不了的先记为 other |
| Template | 细化步骤：把某种模式的粗事务细化成更细的事务，引入一个新对象，带变量、约束、前提、成本项、适用范围和义务（论文的定义，见 22） |
| Chain | 组合链：一串 Template 实例及其变量绑定 |
| Family | 可执行族：组合链＋生成器代码。一个 kernel family 就是一个 Family |
| Assignment | Family 中所有变量的一组取值，对应一个具体 kernel |
| Reference | 外部参考实现，冻结到 commit 或 hash，并在我们的协议下实测过 |
| Gap | 记录缺了什么：参考实现无法表达、与下界的差距无法解释、模型误差过大 |
| Pool | 所有 Pattern、Template、Family、Reference、硬件事实和校准数据的集合；每次变化生成一个不可变快照 |
| Target | 一个硬件目标（GPU 加工具链），提供硬件参数、合法性规则和 microbenchmark |

## 4. 系统做的五件事

| 任务 | 输入 | 输出 |
| --- | --- | --- |
| 求解 case | 一个 Case | 正确的 kernel、性能及其相对下界和参照的位置；不理想时给出 Gap |
| 学习参考实现 | 一个 Reference | 重建为池中的点，或者给出 Gap；以及用于校准的消融数据 |
| 校准模型 | 实测与预测的差 | 修订后的成本模型 |
| 运行实验批次 | 冻结的实验协议 | 结果表、成本表、Gap 汇总 |
| 生成报告 | 记录 | 你阅读用的汇总和图表 |

## 5. 一次求解怎样进行

```
Case → 计算下界 → 检索池中合法的 Template ─(没有)→ agent 构造 Template
     → 求解器用模型选出候选 → 并行编译、检查 SASS、按编译反馈重排
     → 前 k 个做完整正确性检查 → 按协议实测
     → 与下界和参照比较、分解差距
     → 接受 | 模型误差大：校准 | 差距无法解释：扩展空间 | 正确性失败：修 Template
```

除了"构造 Template""扩展空间""校准""修 Template"这几步，其余都是确定性代码，不调用 LLM。详细流程见 [10](10-agent-system.md)。

## 6. 系统怎样变好

- **扩展**：学习参考实现，按 24 把它拆成组合链，补上缺少的 Template 或模式。
- **校准**：用每次实测修正模型。
- **改进**：每批 case 跑完，把不理想的结果按组件归类：空间、模型、意图与 SASS 不符、验证、流程、粒度。损失最大的那类优先改进。属于知识层面的改进由运行时 agent 完成；涉及系统代码的改进，由施工 agent 在你批准后完成。

## 7. 由哪些部分组成

几个相互独立的常驻进程（求解、学习、校准、维护、实验、汇总）各自推进工作，只通过存储和任务队列通信；需要创造性工作时，以"任务"的形式调用运行时 agent。预算分层预留，GPU 正式测量独占进行（见 [11](11-processes-resources-concurrency.md)）。各模块通过接口解耦，GPU 目标、kernel 后端、池子、成本模型、求解器、LLM provider 都可以替换。见 [40](40-modules-and-code-quality.md)。

## 8. 人在哪里

前端让你随时看到：正在运行什么、每个 case 的迭代过程、每个结果的证据链、花了多少钱。需要你的事项进入"待处理"队列，包括批准实验协议、处理升级上来的任务、审查异常结果。你可以暂停、取消、调整预算、发起任务、驳回结果。见 [30](30-frontend-and-supervision.md)。

## 9. 第一阶段范围

**包含：**

- GB10（sm_121），单 kernel 加小范围融合（norm→linear、GEMM＋epilogue）；
- LLM 推理常见算子：GEMM、量化 GEMM/GEMV、attention prefill/decode、MoE grouped GEMM、norm。

**不包含：**

- graph 层和 engine 层优化。Template 预留耦合变量的声明，留待以后扩展。
- 任意的代码合并。自动组合只在声明了接口的槽位上进行（见 [22 §4](22-template-format-retrieval-composition.md)）。
- 自研 LLM 编排框架。
- 宣称全局最优，或宣称完全不需要实测。

## 10. 已有证据（GB10，2026-10）

- F 线 Attention：small 任务上，Template 为 FlashInfer 的 1.488×，文字知识 1.442×，从零 0.835×。medium 任务上文字知识更快，long 任务上三者接近。**Template 的构造成本高于文字知识**，"摊销"目前没有证据支持。
- 一组构造运行中，agent 时间约 52 分钟，GPU 时间约 54 秒。
- GQA decode 的 split 配置在极端输入下数值超限：只测选中的点不够。
- Ventus 上两个资源同时改变，实测与单项效果之积差 1.84 倍：性能模型需要交互项。
