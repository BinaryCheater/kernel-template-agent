# 60 施工与验收

本文讲**施工 agent** 怎样构建 KTA，以及怎样防止"以为做完了"。施工 agent 可以是任何模型，所以本文的约束都不依赖某个特定模型的功能。可以依赖特定模型的地方（例如 Claude Code 的 hook），只作为加强手段。

## 1. 工作方式

- **一个主 agent 负责一个模块，靠 skills 扩展能力。** 尽量不用 sub-agent，不做多 session 编排。
- **交接只通过仓库文件**：设计文档、模块规范、决策日志、交付说明。session 之间不传递长上下文。
- **重复操作做成脚本或 skill**：远端运行、部署、跑验收、写交付说明，都只写一次，之后反复使用。
- **先搭骨架，再并行。** 骨架由一个 agent 完成：每个模块只是最简单的实现，但整条链路真实跑通。接口冻结之后，才让各模块并行填充。并行时，一组文件只有一个写入者。

## 3. 施工顺序

见 [spec/workplan.md](../../spec/workplan.md)。里程碑：M0 探测；M1 不接 LLM 的完整链路（GEMM）；M2 接入 agent；M3 拆解参考实现与覆盖；M4 实验。

**WP10a（手工拆解参考实现）只依赖 schema，可以最早开始。** 它是对知识模型本身的第一次经验检验：拆解中暴露的问题，会在基础设施写完之前反馈到模式表和 Template 粒度上。

## 4. 防止假完成：done gate

每个工作包都有验收脚本 `scripts/gate <WP>`，检查项见 [spec/gate.md](../../spec/gate.md)。施工 agent 必须运行它并通过，才能声称完成。

gate 自动检查以下几项：

1. **代码中没有残留**：mock、stub、TODO、NotImplemented、被跳过的测试，以及只返回固定值的函数。确实需要的测试替身，只能放在测试目录中。
2. **能力有真实运行记录**：任务声明接通的每项能力，都要有对应的真机集成测试通过，或者存储中有真实运行记录。只有单元测试不算接通。
3. **接口合同测试通过**，依赖方向检查（import-linter）通过，Ruff、pyright 通过。
4. **验收测试没有被改动**：验收测试的 hash 与你确认时一致。
5. **交付说明完整**：做了什么；哪些用了简化或 fixture（没有就写"无"）；已知问题；做了哪些决策（同时写进决策日志）。

强制方式：

- 在 `AGENTS.md` 中规定：最后一步必须运行 gate，并把输出贴进交付说明。
- 如果所用的 agent 工具支持结束前钩子，可以把 gate 配进去作为加强，但不依赖它。
- 合入前再由 CI 运行一次 gate。

## 5. 独立验收

每个里程碑结束时，由另一个模型在全新上下文中做一次验收，最好是不同厂商的模型。它只读设计文档、模块规范和代码，按固定清单逐项回答：

- 每项声明的能力是否真实实现，证据在哪里？
- 有没有 mock、toy 实现或硬编码被当成了完成？
- 实现是否违反设计文档中的原则（例如 agent 能写证据、检查器依赖生成器）？
- 有没有设计文档里写了、但代码里没有的东西？

输出的不通过项，作为下一轮施工的输入。

## 6. 你的验收

- **每个里程碑**：你读交付说明、决策日志中新增的条目、独立验收报告，然后在前端看一次真实运行。
- **你不需要读代码。** 但你应该能从前端和记录中看出系统是怎样工作的。如果看不出来，说明可观测性不够，这本身就是一个需要修复的问题。

## 7. 约束本身怎样维护

- 每条约束都要写明它防止哪种失败。来源可以是这个仓库里观察到的问题，也可以是很可能发生的问题。
- 能写成 gate 检查的，就不写成文字。
- 一条约束长期没有拦下过任何问题，同时明显增加了施工成本，就删掉它。
- 每个施工任务记录：耗时、返工次数、gate 和独立验收发现的问题（token 由你的工具统计）。每个里程碑结束时回顾一次，每次只改一项做法。
