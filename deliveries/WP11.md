## What was done

All of the following is code in the repository, checked by unit tests only (claim 0). None of it is a real run.

- **The four remaining processes of docs/design/11 §1.** `kta process start learn|calibrate|experiment|summarize` now run (`processes.IMPLEMENTED == ALL`). Each lives in its own module; `processes.py` only registers them. Work a process does is a `process_action` span on lane `process:<name>`, so the pipeline page shows the processes side by side (D411).
  - **learn** (`proc_learn.py`, D400): checks submitted tasks of expand loops and of tasks booked to `learn`; starts an expand loop for each Reference on the backlog (`kta learn add <reference>`); advances live expand loops (the expand work itself is WP10b's); writes a PoolSnapshot when knowledge was accepted since the current one and moves `current_pool` by compare-and-set. Only this process writes snapshots.
  - **calibrate** (`proc_calibrate.py`, D405):
    - hardware: when the target's newest HwModel is missing or was made on an older Target record, runs WP7's `measure_peaks`; then each microbenchmark of the new suite once per Target record (below). All through the Executor; a failure is stored in `calibrate:hw:error` and retried after an hour, never replaced by a number;
    - refit: after 50 new (Prediction, Measurement) pairs from solve-loop data, fits a new unit-model version with `UnitModel.fit`; it becomes current only if its hold-out error beats the current version on the same hold-out points, else a `calibration` Report records why not;
    - alerts: a (target, family) whose last ≤ 50 pairs have a median signed error beyond 15 % (≥ 10 pairs) gets one T4 (inputs: model, then the pairs, the layout `model_holdout_improves` reads), at most one open per family — the "decode Template predicted low" step of the afternoon;
    - T5: one task per Gap with `missing = hw_fact`.
  - **experiment** (`proc_experiment.py`, D403): only Protocols with an `approve_protocol` HumanAction run; the immutable record is the frozen protocol. Per protocol it builds (if absent) and verifies the batch environment through the registry interface `batch_envs`, i.e. WP8's `kta agents env build/verify` code (D410; `~/.codex` is never read or written); it runs one distinct solve loop per arm × case × repetition (arms interleaved, `max_concurrent` at a time), booked to the experiment process with the protocol's per-run budget as the loop budget and the pinned snapshot, profile, batch and arm condition in the loop data; tags the runs' tasks with the batch; writes one ExperimentRun per finished run (failed and escalated runs included) and, when all are written, the result Report (`title = experiment`, `data.rows`, D345). The set of running protocols drives the quotas.
  - **summarize** (`proc_summarize.py`, `improve.py`, D406): closes an improvement batch on a new experiment result, on `kta improve run`, or daily. It counts Gaps by attribution and judgements by rule (1 → verification, 2 → model, 4 → space), writes the `improvement` Report (D345 fields), creates one T3 per space/granularity Gap that misses a Template or Pattern, leaves model error to calibrate, and holds system-level items in the inbox (`improvement_pending`) until you approve or reject them.
- **Budget hierarchy** (`quotas.py`, D401, D402): configured shares (11 §3.1 defaults, `[budget.quotas]`), the experiment share redistributed in proportion while no experiment batch runs and restored while one runs (applied at every process start and whenever the running set changes), a periodic global budget (`[budget] period`) rolled by the maintain tick with a `budget_period` Report, and `order_queued` (your tasks first, then the process with the least use per share, then priority, then age) for the agent pool. The lower levels (loop, task, job) are WP6's and the executor's, unchanged.
- **GB10 microbenchmarks, first version** (`kta.measure.microbench`, D407), built on WP7's peak harness (`peaks.workload`, `peaks.build`, `peak_kernels.L2`), not duplicating it:
  - `l2_sweep`: the `ld.global.cg` read kernel over 1–64 MiB working sets; one HwFact per point and `l2_effective_bytes` (largest set at or above the midpoint bandwidth) — the regime WP13 B5 relates to model error;
  - `dram_latency`: a one-thread dependent pseudo-random chase → `dram_latency_s`;
  - `launch_latency`: one empty CTA → `launch_latency_s`.
  - Every value is work / median time of a Measurement taken by `Measurer.measure` under the measurement Protocol; HwFacts carry the Measurement refs.
- **T5 path** (`microbench_check.py`, D404): the submission format `microbench.yaml` + CUDA source, the done-check `microbench_repeats` (build once, measure five times, CV below 2 × the Protocol's noise floor), and the accepted output, an HwFact from those same Measurements. WP6's `done_checks`/`outputs` now delegate to it.
- **Runtime skills** `diagnose-model` (T4) and `write-microbench` (T5) in `src/kta/agents/skills/`, catalogued as written; profile `codex-v2` = codex-v1 plus these two (`kta profile write codex-v2`; codex-v1 unchanged; approving it stays your step).
- **CLI** (`cli/process_cmds.py`, one registration line in `main.py`): `kta learn add|backlog`, `kta improve run [--label] [--now]`, `kta experiment status`, `kta calibrate hw`, `kta quotas`, `kta profile write`.
- **Runner** (D409): `Runner.start(..., extra=, distinct=)`, tasks booked to `loop.data.process`; the solve process leaves experiment runs alone.
- **Gate** (D408): `wp11` in `tools/kta_gate/specific_wp11.py`, registered in `specific.py`, tested in `tests/unit/test_gate_wp11.py` (4).

## Known issues

- **Nothing has run on hardware (D320).** The microbenchmarks are untested on sm_121: the chase kernel's modulo and the 64 MiB sweep point may need tuning; the protocol flushes L2 before each launch, so the first of a sweep point's repeated passes is cold; each point reads about 1 GiB, so that pass is at most 1/16 of the work (at 64 MiB).
- **Experiment arms are not enforced.** The pinned snapshot, the arm's knowledge condition and the batch are written into each run's loop data, task bookkeeping and ExperimentRun (with a note saying so), but solve-loop retrieval reads the whole store and WP6's agent step uses `[agents] batch`. Until they read these, arms differ only in their label — WP12 results would not mean anything. See Needed changes.
- **Held-out points of a T4 are visible to the agent.** The card's inputs are both the evidence and the pairs `model_holdout_improves` checks; the skill tells the agent to hold out, but nothing hides them.
- **Hard cap of 3× the task budget** (11 §3.3) and queue-time exclusion are not implemented here; WP8's wall limit kills at the task's wall budget including queueing.
- **Agent pool order.** `order_queued` exists but nothing calls it until WP6's agent-step process uses it.
- **Calibration pairs** come from solve-loop data (Builds are not linked to Candidates, WP6 known issue); experiment runs' pairs are included.
- **Snapshots** are "every usable knowledge record", not an admission decision; Gaps and Reconstructions are not members.
- **Improvement** loss is the unexplained gap share, not microseconds (judgement Reports carry no per-bucket times); step 5 of 10 §2.3 is not done.
- **Loop-state spans of experiment runs** are on lane `process:solve` (WP9a convention); the experiment's own actions are on `process:experiment`.
- **Concurrency.** Process state pointers are compare-and-set; two instances of one process are prevented by WP6's process lock, but a CLI `kta improve run --now` during a summarize tick can write two Reports for overlapping windows.
