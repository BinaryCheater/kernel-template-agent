# WP24 delivery: verification in the loop

Branch `wp/WP24` from `integration` (85c7351). Code stage (D320); the checker also ran for real in `$KTA_DATA/dev/WP24` (CPU only, no model calls). Decisions D630–D643.

## What was done

**Part A — checker** (`kta.checks.proof`, layer 6; imports core and store only; import-linter keeps `checks` away from `knowledge`). New dependency `z3-solver` 5.3.3, locked by uv (D630).
- Condition builder `encode.py` / `space.py`: the expression language as Z3 terms (Python floor division and modulo encoded exactly, `/` real, `ceil_div`, `min`/`max`, `is_pow2`, string enumerations with an "anything else" value, sorts inferred from use); constructs without a faithful encoding (`log2` of a variable, a variable exponent) raise `Unsupported` → `unresolved`.
- Three outcomes plus `bounded`: `proved` (full declared domain), `bounded` (bounded model or bounded enumeration), `counterexample` only after the independent interpreter confirms the witness (`kta.core.expr` evaluation for contract conditions; token replays for the models), `unresolved` for unknown, timeout, unconfirmed witness or unsupported construct. Each ProofResult stores the SMT-LIB sha256 of every query, the stated domain, the counterexample and the replay.
- K2 models (open table `MODELS`): `tile_index` (coverage / exact-once / no-phantom / injective origin, symbolic tile over the whole domain, every extent), `slot_rotation` and `slot_progress` (bounded event model of paper Appendix A, W warps × KT = max(phases, S+P+2) phases, token replay), `partition_index`, `event_order`, `resident_capacity`, `async_readiness`, `bank_map`, `queue_progress`. Reimplemented after the read-only reference `/Users/dingyi/Projects/agentic-codesign/backend/ventus_compiled/proof_templates/upstream/smem_verify.py` and `queries.py` (nothing imported).

**Part B — K1–K3 once per Template.** `check_template`: K1 per precondition (a `same_as` link is reported confirmed only after the checker proves the equivalence), K2 through the outline's models, K3 (inline disjunction or quantified query, witness replayed by enumerating X). Outline assumptions may name only p.* / hw.* / case.*; one naming a design variable is refused (an unproved statement never becomes an assumption); Γ ∧ assumptions must be satisfiable. Proof outlines are a record kind `ProofOutline` (D631), seeded in `knowledge/seed/proofs/` and proposable by an agent as `proof.yaml` in a T3 workspace (skill `write-template` step 9). Seed addition: the paper's Listing 1 as `shared_memory_tiling@1` (D637).

**Part C — composition (Theorem 1)** `prove_family`: each step's K1 and K2 under its chain bindings (fixed / aliased variables, p.* bound to family expressions, Target hardware values), π feasible-to-feasible as "every feasible family design and case satisfies each step's Γ" (witness replayed), assumption compatibility (discharged by bindings, guaranteed by a finer step, or declared for the whole result); weakest step's level otherwise, with named gaps (D640).

**Part D — once per candidate** (`orchestrator/proofgate.py`, in `work_solving` after `record_solve`): Γ, C and Pre of every chain step at the assignment, by the interpreter (not the encoding). Violations are dropped and recorded; unbound workload parameters are `unknown`; `claims` is `correctness` only with a bounded/proved composition, else `exploration` (D638).

**Part E — proof reuse** (`records.py`): premises are hashes of the named groups a result uses plus solver and checker versions (the checker version is the content hash of the trusted base). Equal premise keys reuse live certificates (`refs.reused`); `kta prove drift` invalidates on a changed checker / solver / superseded outline and propagates through refs (`kta.store.stale`). Assurance bounded / proved is read only from the newest live ProofSummary (`kta.store.assurance.effective`, used by the pool, coverage, retrieval and the API; D634).

**Part F — weakest precondition and Δpre** (`wp.py`, `kta prove wp`): Safe from the per-point model; exact / stronger / unsound; for stronger the simplest linear predicate equal to Safe on the menu, re-verified before recording. The solve loop re-solves with "stronger" steps relaxed and passes `relaxed_pred_us`; `gap.decompose` gives Δpre as a value, with a note naming each step's relation, or `not_assessed` (D639).

**Part G — frontend.** Pool: assurance strip (declared / tested / bounded / proved) and an obligations column per Template (each obligation of Σ with outcome, stated domain, method, reuse and record; K1/K3 rows; unchecked and never-checked obligations listed; last run, checker and solver versions). Result: a "Proved vs tested" panel (composition level and gaps, each step's assurance in the chain, candidate gate and claims, code-level checks: numeric tests, SASS intent, sanitizer, canaries; what no proof covers). API: `/pool` `proof` + `assurance`, `GET /proofs/{id}`, `/lineage` `result.assurance`. Checked in the browser against the dev store (API on 127.0.0.1:7324, `vite preview` on 127.0.0.1:4184).

**CLI**: `kta prove template|all|family|wp|drift|status|canary`.

**Real runs** (evidence `deliveries/WP24.evidence.json`, commit f933f6b, clean, `dev/WP24`): `kta prove all` (all seed outlines), `kta prove canary`, `kta prove wp` (tiling and rotation: exact), `kta prove family … --from-dir --target gb10` with and without the arbitration declaration, `kta prove drift` after a checker change (109 records stale; the next run reused nothing, the one after reused every positive certificate). Whole seed: a few seconds on the Mac (multi_buffer_rotation's 128-point event model is the largest part); composition under 1 s (D642: in-process, no Executor job).

Reading the counterexamples (all replayed; the seed Templates are unchanged, D643):
- **K1 on physical_storage, output_tiling**: their preconditions mention only p.* (`p.last_read + p.delta <= p.next_write`, `p.independent_outputs`), so no constraint C can imply them; they belong in Γ.
- **K3 on multi_buffer_rotation, physical_storage, shared_resource_binding**: Γ admits parameters for which C is empty (negative capacity, `p.wavefronts` not equal to its definition, `size * copies > capacity`).
- **K2 async_transfer.readiness**: `complete_point = before_read` read as a warp-local wait (no barrier): with two issuing warps a read precedes another warp's completion.
- **K2 shared_resource_binding.bijective_binding**: `padding` is not a permutation of the tile's addresses as the obligation and π state (it is injective onto a larger space).
- **K3 reduction_partition**: `unknown` from Z3 on the quantified query (wide domains); `runtime_balanced` has no index function.

## Known issues

- Not covered, and stated as such in the UI: generator code vs the Template's abstract program, FP rounding, schedules beyond the bounded model. Code-level claims stay `tested`.
- Encoding-implies-C is not proved at the Template level (D641); the candidate gate re-checks C per chosen point.
- No seed Template other than the paper's tiling template reaches a level; the reasons are listed per obligation above. The candidate gate therefore marks every seed-family candidate `exploration`.
- `async_readiness` cannot model `compiler_pipelined` (the seed family's binding), so ab_async stays unresolved in the chain.
- `kta prove family --from-dir` records a family directory's Chain and Family itself (needed for the seed family, which has no other import path); the orchestrator still writes families from T1 outputs.
- The Δpre relaxed solve runs a second solve per bucket only when some chain step has a "stronger" record; none does in the seed, so it has not run inside a real solve loop.
