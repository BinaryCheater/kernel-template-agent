# WP19 delivery: FormulationPlan, chain enumerator, access discipline, and the WP17 projection compiler

Branch `wp/WP19`, code stage (D320): no real run, no GPU job, no experiment. WP17 is folded in (D328). Decisions D540–D550. Design source: docs/design/02 §5.1–§5.5, §6.2; 22 §3.3, §5; 10 §4.4.

## What was done

Every capability below is shown by unit tests on the control host only (`deliveries/WP19.evidence.json`, one code-stage claim, output `Mac.lan:~/kta-data/dev/WP19/evidence/pytest-8c570a4.txt`, no store record). None has run against real hardware or a real agent.

1. **Projection compiler (WP17; D546).** `src/kta/solve/projection.py` compiles a formulation's bound effects, a plan's fixed values / menus / outer variables and the `MachineModel` into the MIP of L1's steady-state projection at peak. Its parts are ResMII (`T >= busy_r`, epigraph max), pair bounds (`T >= u_a + u_b`), RecMII (`T >= trips·(lat_a + lat_b)/inflight`), serial terms in the objective, walls as rows, and constraints as linear or table rows. Effects are encoded with one-hot menus, menu products and table terms (joint indicators linked to the menus; `tbl.*`, `min`, `ceil` evaluated inside), integer-ceil columns on the linear path, and outer enumeration for what fits neither. The agent writes none of it. KT (a 1..65536 range) is narrowed to its reachable values by the constraints that pin it. Tests: `test_gemm_seed_formulation_compiles_and_solves` (objective = `projection_us` = `compose(price_parts(...))` at every returned point; rules used: one-hot, ResMII, table terms), `test_projection_is_the_minimum_of_enumerated_projection` (the MIP optimum equals the minimum over the enumerated space, shape 1024×1024×16384), `test_outer_enumeration_and_its_limit`.
2. **Comparison arm (D-T1, D547).** `solve(..., projection={...})` takes the compiled projection (method `projection`). Without it, `solve` keeps the existing path. Its MIP export of the hand- or agent-written formulation is now labelled the comparison arm (`mip.COMPARISON_ARM`, a note on every MIP solve). Test: `test_solve_selects_the_projection_arm`. The locked WP5 acceptance tests pass unchanged.
3. **FormulationPlan (D540, D541).** The record kind `FormulationPlan` covers F1–F7: chain, bindings, each variable's status, value and menu with the structure it invokes and the evidence it cites, table terms, glue, dispatch, generator, and citations for the other sections. `solve/plan.py` provides `default_plan` (the deterministic default as the same object), `plan_inputs` (a plan → compiler inputs), `diff_plans`, `score_plan` and `record_plan`. The score counts changes and uncited non-default decisions (knob `guard.evidence_citation_in_plans`; stop rule `complete`), and compares open dimensions, space and projection bound against the default. Tests: `test_default_plan_for_the_gemm_seed_case`, `test_agent_plan_fixture_is_diffed_and_scored` (fixture: one cited fix of BM, one uncited menu cut of threads, one uncited glue addition; the restricted plan's bound is ≥ the default's).
4. **Chain enumerator (D542).** `solve/chains.py` expands a bounded derivation over the Template grammar. A symbol is (pattern, level) and every start symbol is refined. Filters: capability on the target (WP14), Γ false (Γ unknown counted), and `excludes`/`requires`. Each chain is bounded by the SOL of the minimal work on the resources it reaches and pruned against an incumbent. It reports coverage counts (missing rules, rules per symbol, chains per Template, filter counts, exhaustive or not) and the best-bound chain (the F1 default when there is no retrieved chain). Test: `test_enumerator_finds_the_seed_chain_within_its_bound` (the seed chain is found at bound = max SOL; an incumbent below SOL prunes it; an unknown start symbol is reported as a missing rule).
5. **Composition statistics (D543).** A derived view over Chain records: co-occurrence, order, and conditional frequency "pattern@level → Template". Served at `GET /composition`. Test: `test_composition_stats_is_a_view_over_chains`.
6. **Access discipline (D544).** The versioned table is data in `src/kta/core/access_discipline.yaml`: v1 holds the nine rows of 02 §5.4, each with machine-readable pulls. `src/kta/core/access.py` loads, classifies and renders it. The worker skill `use-kta` carries the rendered table between markers, plus a section on the header; `find-knowledge` points to it. The one-screen task header comes from `orchestrator/access.task_header` and covers case, bound, the last round's gap, the default plan and its score, budget, and the situation with its fetch/decide row. It holds at most 24 lines (knob) of at most 100 columns. TaskCard schema 2 has an optional `header` (identity upcast); `TaskRequest.header` writes it into the card, and TASK.md starts with it. Tests: `test_header_fits_one_screen_and_states_the_situation`, `test_skill_carries_the_rendered_table`, `test_task_md_starts_with_the_header`.
7. **Pull log (D545).** Every worker `kta show / card / why / query` reaching the agent API writes one `Pull` record: task, command, target, kind, situation, the table row it matched (or none: outside, allowed) and the table version. Views: `GET /pulls?task=` (per task), `GET /pulls` (across tasks: the system loop's input for revising the table), `GET /plans/{id}`. The Release page's held calls now show the task's pull log and the plan its header names, with the diff. Test: `test_pull_log_written_for_a_task_and_shown_on_release`. This drives the token endpoints the worker's `kta` uses in client mode for a leased task whose card has a header; the fake Codex adapter itself does not call the API (see Known issues).
8. **Knobs (D549):** `formulation.table_max_entries` 4096, `formulation.outer_max_points` 256, `formulation.chain_max_steps` 12, `formulation.chain_max_expansions` 2000, `session.task_header_max_lines` 24. They are in the registry, `Knobs` and 12 §7. The consumers of `session.access_discipline_version` and `guard.evidence_citation_in_plans` are now named.
9. **Spec, gate, logs.** spec/schemas.md §4.8.1 and the TaskCard `header`; formulation-solve-models.md "Projection compiler" and "FormulationPlan and chains"; orchestrator-cli.md, api-web.md, agents.md; spec/gate.md WP19 row; `tools/kta_gate/specific_wp19.py` registered in `specific.py` (D550); changelog entry; review-queue entries for D540/D541, D542, D544/D545, D546/D547.

## Fixtures and simplifications

- No `# kta:fixture` in `src/`.
- Test-only data: the agent-plan fixture in `test_agent_plan_fixture_is_diffed_and_scored` (its evidence IDs are placeholders, not records), the `FormulationPlan`/`TaskCard` records written in the pull-log test, and a Chain record written in the composition test.
- Simplifications, each a decision. The projection is at eff = 1 without interaction terms, a lower bound of L1 (D546). `lower_occupancy` walls enter as residency ≥ 1 (D546). The default plan takes the family's own glue and dispatch (D541). Γ unknown keeps a step, counted (D542). A chain's bound uses only the resources it reaches, and a chain that misses one is unbounded, never pruned (D542). Situation comes from the last gap class (D544). The "MIP too large" and "non-algebraic effect" situations are never derived automatically: the caller passes `situation=` (D544).

## Known issues

- The MIP ↔ L2 consistency check is not implemented. `projection.consistency_check` raises NotSupported until WP16 merges (D548). The gate reports it as WARN. The "deliberately wrong reservation table" fixture belongs with it.
- No producer of case-loop task headers yet. `TaskRequest.header` and `task_header` exist, but the orchestrator's case loop (WP18's routing) does not yet build them, so today's tasks log pulls with situation "" (all outside).
- The fake Codex adapter does not call `kta`. The pull-log acceptance drives the same API endpoints with the task's token rather than through a fake-adapter session.
- The compiled projection is not `solve`'s default (D547). Flipping it is one argument, after X11 and the L2 check.
- The enumerator reads start symbols from a reference chain (`start_symbols`), because Problems do not list their transactions. With 7 seed Templates its search is small; on the 30 reference Templates the expansion budget (2000 nodes) may stop it, reported as `exhaustive: False`.
- Composition statistics count list order, not the `after` DAG. The gap-conditioned form ("bottleneck X → move Z") needs WP18's gap records.
- The plan score compiles the projection only when the plan keeps the formulation's chain. A changed chain needs its own formulation (noted in the score).
- `use-kta` changed, so its skill hash changes. The next approved AgentProfile carries it; stored profiles keep the old skill.

## Design interrogation

Full pass over the spec interface changes (schemas §4.8.1, TaskCard `header`; module interfaces in formulation-solve-models, orchestrator-cli, api-web, agents). Each mechanism gets the nine questions. The adversarial second pass is due at the milestone.

### M1: FormulationPlan (schemas §4.8.1)

1. *What*: the agent's formulation decisions F1–F7 as one structured record, with the deterministic default as the same object. It is not a Formulation (that stays assembled from the chain) and not a solve result.
2. *Claim*: plans are diffable and scored against a default (D-T18, D-T19); every non-default decision cites a structure and evidence (01 §7.1).
3. *Depends on*: given: the Structure records (paper Table 1) and record IDs as evidence. Assumption: F1–F7 cover what an agent decides about a formulation.
4. *Scope*: one family and chain per plan. Multi-chain plans (branches) are written as several plans.
5. *Fails by*: citations that name unrelated records (gaming the check); a default that drifts with code changes, so diffs change meaning; an agent restricting menus to look fast.
6. *Observable*: `score_plan` (uncited list, space, bound vs default). Plan records keep their `default` ref, so a re-derived default can be compared. A restricted plan's bound is ≥ the default's (test).
7. *Knob*: `guard.evidence_citation_in_plans` (true).
8. *Repair*: a new plan record (never an edit). A changed default derivation is a decision row; old plans keep their old default by ref.
9. *Decides*: assistant default (D540, D541), needs user review. Alternatives not taken: free-text plans; a default without the family's glue. Cost of changing later: medium (schema version + upcast).

### M2: Chain enumerator and composition view (formulation-solve-models "FormulationPlan and chains")

1. *What*: a bounded derivation over Templates as rewrite rules, with filters, a SOL bound and incumbent pruning. It is not retrieval by similarity (`nearest_chains`) and not a solver.
2. *Claim*: a deterministic F1 baseline; missing rules exposed; coverage counts (02 §5.5, E12).
3. *Depends on*: given: Template `refines`/`produces`/levels, capabilities, Γ, minimal work. Assumptions: (pattern, level) symbols are a faithful grammar; start symbols can be read from a reference chain.
4. *Scope*: pools where Templates rewrite one symbol each; branching chains appear as sets of steps.
5. *Fails by*: an exploding expansion; a grammar that cannot derive a real chain (missing produced symbol); bounds too loose to prune anything.
6. *Observable*: `coverage()` (missing rules, filter counts, `exhaustive`); seed chain found (test); `pruned_incumbent` count.
7. *Knob*: `formulation.chain_max_steps` (12), `formulation.chain_max_expansions` (2000).
8. *Repair*: add the missing Template (knowledge loop) or a grammar rule (decision row); the counts show the effect on the next run.
9. *Decides*: assistant default (D542, D543), needs user review. Alternative not taken: an authored grammar file. Cost of changing later: low.

### M3: Access discipline, task header, pull log (schemas §4.8.1, orchestrator-cli "WP19", api-web, agents)

1. *What*: a versioned situation → fetch → decide table, a one-screen header that states the situation, and one record per fetch that matched a row or did not. It is not an access control: pulls outside the table are allowed.
2. *Claim*: context discipline makes retrieval measurable and revisable (D-T20, 02 §6.2 system loop).
3. *Depends on*: given: the agent API is the only path to knowledge in client mode (D370). Assumptions: command + record kind identify the fetch type; the last gap class identifies the situation.
4. *Scope*: workers in client mode. Local `kta` (human, no token) is not logged.
5. *Fails by*: the situation is wrong (WP18 not wired), so every pull counts as outside; a worker over-fetching inside the row; Pull volume growing large.
6. *Observable*: `GET /pulls` (in-table share, outside by situation and pull); the header on the Release page; the gate checks that skill and data agree.
7. *Knob*: `session.access_discipline_version` (v1), `session.task_header_max_lines` (24).
8. *Repair*: a new table version from the pull statistics (system loop); old Pull records keep their version.
9. *Decides*: assistant default (D544, D545), needs user review. Alternatives not taken: Markdown as the single source; logging from spans (prunable, not evidence). Cost of changing later: low.

### M4: Projection compiler and the comparison arm (formulation-solve-models "Projection compiler")

1. *What*: deterministic translation of chain effects + plan + hardware model into a MIP whose optimum is L1's projection optimum at peak. It is not a simulator (L2) and not the hand-formulation MIP (kept as the comparison arm).
2. *Claim*: the agent writes no MIP; translation correctness is the compiler's (02 §5.2, R1, R4).
3. *Depends on*: given: WP15's effects, MachineModel and `price_parts`/`compose`. Assumptions: menus are small after narrowing; atoms depend on few variables.
4. *Scope*: finite-menu formulations whose atoms tabulate within 4096 entries or are linear up to `ceil`; the rest goes to outer enumeration up to 256 points.
5. *Fails by*: an atom over many variables (NotExportable, or slow outer enumeration); an undefined combination silently excluded where it should be an error; efficiency/interaction relaxation hiding a real ranking difference.
6. *Observable*: `ProjectionOutcome.rules`, `outer`, `notes` (why each variable went outward); `undefined_excluded` count; objective = `projection_us` at each point (test); after WP16, the MIP ↔ L2 check.
7. *Knob*: `formulation.table_max_entries`, `formulation.outer_max_points`; `solve(..., projection=)` per call.
8. *Repair*: the L2 check names the effect with the largest deviation, then a model or effect fix (WP15/WP16 maintenance loop), then re-check.
9. *Decides*: assistant default (D546, D547, D548), needs user review. Alternatives not taken: big-M products; making the projection `solve`'s default now. Cost of changing later: low.

## Follow-up: MIP ↔ L2 consistency check (after WP16, branch `wp/WP19-check`)

- `src/kta/solve/consistency.py` (D551, supersedes D548): `consistency_check(f, shape, mm, l2_mm=None, rank_min, violation_max, samples, seed)` enumerates the feasible points (seeded sample above `samples`), evaluates `projection_us` (= MIP objective) and `models.l2.simulate`, passes when Spearman ρ ≥ rank_min and MIP > L2 on at most violation_max of the points, and on failure names the transaction with the largest priced-time deviation (else `schedule:<bottleneck>:<idle category>`). The stub in `projection.py` is removed.
- Knob `model.mip_l2_check` {rank_min 0.5, violation_max 0.05, samples 128}, set_by X11; X11 `sets` lists it (moved out of `sets_elsewhere`); row in 12 §7.
- Tests: `test_mip_l2_check_passes_on_the_gemm_seed_family` (4096³ and 1024×1024×16384: all 70 feasible points, no MIP > L2, ρ 0.52–0.54) and `test_mip_l2_check_fails_naming_a_wrong_reservation_table` (fixture: the projection's model reserves 4× the tensor work per mma instruction, the simulator runs the seed model; fails with the effect `mma.mma`). Gate check "MIP <-> L2 thresholds set by X11" replaces the WARN.
- Known issue: ρ on the GEMM seed is only just above the default 0.5. L2 exceeds the projection up to 2.5× at shallow pipelines (WP16 known issue: L1's recurrence counts latencies only), so the projection prunes more than it ranks there; X11 sets the real threshold. With one shared hardware model, a wrong reservation table affects MIP and L2 alike and cannot be seen by this check: it detects a projection compiled against a model other than the simulator's, and simplification error of the projection itself (via ρ and the bound).
- Pending real run: X11 (distribution of ρ and violations over the GEMM family subspace) to set `model.mip_l2_check`.
