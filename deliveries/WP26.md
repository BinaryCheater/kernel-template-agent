# WP26 delivery (first part): one hardware-model engine, copied from upstream

Branch `wp/WP26` from `integration` (94b639c). Code stage, first part: copy step, parameter step, L3 entry on a KTA Build. L2/L1 from the engine and the Executor-backed L3 are not done. Decisions D680–D683. Design: `docs/design/25-hardware-model-sources.md`.

## What was done

**Copy step (D680, D681).** `src/kta/models/gb10sim/` is the GB10 simulator of AI-Infra-Co-Design `agentic/gb10` at commit `0eef497` (`/Users/dingyi/Projects/ai-infra-codesign-ventus`), with its parameter file `gb10.json`. That covers the SASS reader, the SM simulator under the compiler's control bits, warp-specialized TMA, grid mapping, the analytic traffic functions and the two validation drivers. The README lists the upstream file hashes and every change. Behaviour-preserving changes only:
- formatting and re-wrapped comments;
- type declarations;
- the calibration directory is passed as an argument;
- results are returned, not printed;
- KTA's Spearman instead of scipy's.

The calibration data (SASS dumps and ablation records, 35 MB) is not in git. `scripts/gb10sim-replay` replays a validation set on a calibration directory.

**Replay on slai (CPU, manual via `scripts/remote-run`, not the Executor).** The upstream code (verbatim, with a 15-line scipy shim for the printed rank correlation) and the copy ran on the same calibration copy, `/storage/kta-work/wp26/upstream-0eef497/calibration/spark-6951`.

**Parameter step (D682).**
- Every `gb10.json` entry has a status: 30 measured, 11 fitted, 13 structural, 1 withdrawn. The simulator's own block has 40 measured and 2 assumed.
- The hardware numbers upstream wrote in code are now named entries: a second clock of 2.54 GHz next to `clock_GHz` 2.52, launch 2.6 µs, graph launch, DRAM datasheet and rate floor. Existing entries replace the TMA rates, DRAM rate, occupancy limits, SM count and block setup.
- ISA facts stay in code.
- Instructions on the assumed latency fallback are counted per opcode. On the 22 kernels they are only prologue constant and special-register reads: `LDC.64` 816, `S2R` 612, `LDCU.64` 212, `LDCU` 204, `S2UR` 204.

**L3 on a KTA Build (D683).** `kta.models.gb10sim.l3.simulate_build` runs the engine on a Build's `sass` blob. The reader learned cuobjdump's format (`Function :` header, numeric branch targets) next to nvdisasm's, with tests for both. Only TileLang's cp.async GEMM lowering is mapped; TMA and other kernels raise NotSupported.

First real run, on slai with commit ff8a469:
- Input: Build `cfea656e…` from SYSDEBUG1 on spark-hk, `gemm_fp16_tilelang` with BM=BN=128, BK=32, S=3, 128 threads, 4096³ fp16, 202 registers, L2 flushed as KTA's protocol does.
- Its k-loop is the same instruction mix as upstream's calibrated `c128x128x32_st3_th128`: 64 HMMA, 16 LDSM, 8 LDGSTS.
- **L3 predicts 1893.0 µs**: 1024 tiles, 2 blocks per SM, 11 waves, 403 MB from DRAM, L2 miss fraction 0.19.
- KTA's L1 for the same candidate (Prediction `b08df6531808`, bucket s0) says **1162.0 µs**, tensor-bound. Its tensor term implies 118 TFLOP/s, above the contract's sustained 95 TFLOP/s chip rate and close to the per-SM mma pipe rate at boost clock (1024 FLOP/clk × 2.52 GHz × 48 = 124 TFLOP/s).
- The two levels disagree by 63 % because they read different parameters. This is the inconsistency WP26 removes. No measurement of this Build exists, so neither number is checked.

## Fixtures and simplifications

- `kta:fixture` markers in `src/`: none.
- The replays and the L3 run were manual construction runs on slai through `scripts/remote-run` and ssh, not Executor jobs. Nothing was written to a KTA store, so `deliveries/WP26.evidence.json` is empty.
- The scipy shim was used only for the upstream baseline run's printed correlation, in `/storage/kta-work/wp26/upstream-0eef497/shim`.
- `l3.simulate_build` reads holes from the caller. For the real run they came from the Build's generated `kernel.py` by hand; no code extracts them yet.

## Known issues

- **Two clocks.** 2.52 GHz in `validate.py`, 2.54 GHz in kernel/TMA code: kept to stay bit-identical, needs reconciling.
- **Two tensor peaks.** Upstream measured the per-SM mma pipe rate (124 TFLOP/s at boost clock) and the sustained chip rate (95 TFLOP/s). KTA's L1 uses something close to the former.
- `ws.py` uses `C["tma_l2_aggregate_GBs"]` (1860, fitted from an ablation), while upstream's docstring cites a 1.58 TB/s probe.
- The loads-only block-level error is large: median 16 %, worst 78 %. This is upstream's own open item (copy completion under load).
- TMA set: pending at the time of writing (see below).
