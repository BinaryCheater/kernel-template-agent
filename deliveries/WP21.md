## What was done

### Controls registry (R11, D480, D481)

- `src/kta/core/controls.yaml` defines **every row of docs/design/12** (39 rows of §1–§4) plus 12 rows the code already used or D325 set (new 12 §7): 51 knobs. Each has its value type and bounds, initial value, the failure it prevents, where it lives (profile / orch / protocol / ui / gate / knowledge), status (spec / default / set, with its source), `set_by` (X experiments), `editable` (false for the five invariants of 12 §3) and `consumer` (the code that reads it, or "pending WP18/WP19/WP14/WP16/WP20").
- `src/kta/core/controls.py` validates the definitions on load (types, unique ids and accessors, initial values valid, `set_by` ⇔ experiments' `sets`); `Controls` is a frozen snapshot with `with_changes` (validated proposal; invariants refused), `diff`; `src/kta/core/knobs.py` has **one typed accessor per knob**. The registry sits in layer 0 (`kta.core`), so orchestrator, agents and api all read it; `Context.controls` carries the snapshot for pure code.
- `src/kta/store/controls.py`: versions as **ControlsVersion records** (new kind, spec/schemas.md §4.10) and the pointer `controls:current` (compare-and-set). `ensure` writes version 1 (system actor) and a system version when the definitions gain or lose knobs (stored values kept). `propose` writes a human's version with a reason; it refuses a stale `expected` version, invariants, invalid values and no-op proposals.
- **Every run records its version**: `refs.controls` on TaskCard (the version its budget came from), AgentRun (the version of that step) and ExperimentRun (the list of versions its loop ran under); loop data `controls` and `controls_seen`.
- **Scattered constants removed** (D482, D483): orchestrator `Settings` is `Settings.of(controls)` with no defaults (solve/expand round limits, judging thresholds, shortlist, top-k, lease, card budgets, attention cap, infra retries, ε); `budget.QUOTAS` and `[budget.quotas]`; inbox `REPEAT_FAILURES`, `BUDGET_WARN`; agent runner `LEASE_S`, `RENEW_EVERY_S`, `3 ×` hard cap, idle 600 s, wall budgets from the profile; sessions `DEFAULT_RESET_RATIO` and the twice-rule; cards `STEP_HEADER_MAX_CHARS`; `[agents] slots`; machines.yaml numeric limits (now knob names, resolved by the API). Old config keys are refused with the knob to use. The gate scans `src/` so they do not come back.
- Docs: `docs/design/12-agent-controls.md` has a `set_by` column on every row (changelog next step 7), an "Implemented" paragraph and a new §7. `spec/modules/core-store.md` "Controls registry" says how WP18/WP19 add a knob (one YAML row + one accessor + one row of 12; tests enforce all three).

## Design interrogation

Full pass over the spec interface changes (registry + ControlsVersion schema; staged release; settings write path).

### Mechanism A: controls registry and versions

1. **What is it?** One table of every knob that governs agent spending, cut-offs, sessions, anti-gaming and escalation, with its current value as a versioned record. It is not general configuration (paths, hosts, workers stay in `config/kta.toml`) and not the AgentProfile (prompts, skills, model).
2. **Claim served.** "Parameters are set by small experiments, not by fiat" (01 §3) and supervision without reading code: you can see and change every knob, and every result says which values produced it.
3. **Depends on.** Givens: 12's rows; the store's immutable records and CAS pointers. Assumptions: one control host per data directory; 51 knobs stay small enough for one page.
4. **Where it holds.** All processes, the agent runner and the API of one data directory. Workers do not read it (they get values through cards and launch specs).
5. **How it fails.** A value read from somewhere else (a leftover constant); a definition default edited and assumed to apply; a version written but a running process using an old snapshot; a value set without a reason; a knob added in code but not in 12.
6. **How we would know.** Gate scan for replaced constants; `refs.controls` on every run record; tests that 12 rows, YAML rows and accessors agree; the version page shows author, reason and changes; `GET /controls` shows `stored_under_hash` vs the current definitions hash.
7. **Knob.** The registry itself; its own rule (who may write) is fixed: a named human with the operator token.
8. **Repair.** A wrong value: write a new version (the old stays as evidence); a wrong definition: change the YAML and the code, `ensure` writes a system version on the next run.
9. **Who decides.** Assistant defaults D480–D483 (review queue). Alternatives not taken: TOML config section (unversioned), values only in AgentProfile (would split orchestrator and agent knobs). Reversal cost: medium (store module and API).

### Mechanism B: staged release

1. **What is it?** A system-wide stage S0–S4 that limits which processes tick, which task types an agent may take and whether each agent call needs your release. Not a pause (pause is per scope and temporary; the stage is a deliberate release level).
2. **Claim served.** "No stage opens until we understand and have debugged the previous one" (01 §3); controlled runs before autonomous token spend (01 §5).
3. **Depends on.** Givens: the agent pool is the only automatic path to an agent call (step_once). Assumption: one runner in S1.
4. **Where it holds.** Automatic agent calls and process ticks; not manual `kta task lease`, not loops already in progress (they still create tasks, which wait).
5. **How it fails.** Two runners both start a call (race); a release reused for a retry; you release without reading; tasks pile up unseen in S0; the stage is opened without its exit criteria met.
6. **How we would know.** Held calls listed with reasons on the Release page and `GET /release`; the HumanAction per release names the attempt; the stage change is a version with a reason; tasks in flight shown.
7. **Knob.** `release.stage` (default S0, orch + UI); stage contents in `stages.yaml` (code review to change).
8. **Repair.** Move the stage back with a new version; cancel a task; the release pointer is per attempt, so a retry needs a new release.
9. **Who decides.** Stage changes are yours; D485 (S0 default, gate in the pool) is the assistant's default, in the review queue. Alternative not taken: gating inside `TaskQueue.lease` (atomic, but changes every lease caller). Reversal cost: low.

### Mechanism C: settings write path

1. **What is it?** The only way to change a knob value: `POST /controls` with the operator token, the version read, the changes and a reason. Not the operations endpoints (`/actions/*`), which change runtime state, not knob values.
2. **Claim served.** Every value has an author and a reason; nobody overwrites a change they have not seen.
3. **Depends on.** The token file on the control host; the API bound to localhost.
4. **Where it holds.** One control host; one user.
5. **How it fails.** Token leaked or absent; an agent writing values; a stale page overwriting a newer version. This pass found that the task-token endpoint `/write/record` accepted any kind except HumanAction and StatusChange, so an agent could have written a ControlsVersion record (it could not move the pointer, so it would never take effect). Fixed in this branch: ControlsVersion is refused there too (`test_a_task_token_cannot_write_a_controls_version`).
6. **How we would know.** 403 without token; `expected` mismatch is 400; versions list shows author and author type.
7. **Knob.** `[api] operator_token_file` (configuration, not a control).
8. **Repair.** Rotate the token by replacing the file; write a corrective version.
9. **Who decides.** D486 is the assistant's default (review queue). Alternative: guard all write endpoints. Cost: low.

### Adversarial pass (author's own; the fresh-context pass belongs to the milestone review)

- **Choices the user did not make:** D480–D489; 12 §7 rows added to the user's design document; S0 as the starting stage; T4–T6 wall budgets now follow 12 (shorter than the code had); the operator token only on settings writes; process quota 10 % split 5/5.
- **How an agent could pass the checks without the intended work:** a WP could add a constant and read it instead of a knob under a new name (the gate scans only the known names) — reviewers should look for numeric literals in decision code; a knob could be added with `consumer: pending` forever — the Settings page shows the consumer, and a knob that prevents nothing should be removed (12 §5).
- **Bridges:** downward a ControlsVersion (system loop → every loop); upward `refs.controls` on run records. Nothing else crosses.
- **Questions you may ask that the design does not answer:** who may move from S1 to S2 and on what evidence (exit criteria are text you judge); whether an agent task may be released in bulk; whether an experiment arm may run under different controls than the system (X5 needs two retry values at once — today a version is global; an arm-level override is not built).
- **"Later" items recorded as obligations:** pull log and plan on the Release page (WP19); the knobs marked `pending WP18/WP19/WP14/WP16/WP20` (their consumers); the arm-level override for X experiments (not recorded elsewhere yet — listed here as an obligation for the X protocol work).
