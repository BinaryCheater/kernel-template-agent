# WP18 delivery: gap decomposition, routing and loop disciplines

Branch `wp/WP18`, code stage (D320): no real run, no GPU job, no experiment. Decisions D520–D530. Design source: docs/design/02 §1 (P1, P6, P7), §6.1, §9; 12 §3–§4; D324, D325.

## What was done

Every capability below is shown by unit tests on the control host only (`deliveries/WP18.evidence.json`, one code-stage claim, no store record). None has run in a real case loop.

1. **Gap decomposition per round** (D520; `src/kta/orchestrator/gap.py`). `T_meas − T_SOL = ε + δ + Δpre + L_rep + irreducible` per bucket: ε against the solver's best prediction; δ from the solve certificate (0 if model-optimal, `mip_gap × P1` for a MIP, else `unbounded`); Δpre and irreducible are `not_assessed` until their inputs exist; L_rep ≤ P1 − T_SOL. Each judged round writes a **GapDecomposition** record (new kind, spec/schemas.md §4.8) with the bucket inputs, terms and statuses, class, route, routing version and the discipline verdict; the judgement Report links it (`refs.decomposition`). Tests: `test_terms_sum_to_the_gap_and_sol_bounds_l_rep`, `test_unassessed_terms_are_labelled_not_zeroed_silently`, `test_mip_gap_bounds_delta_and_attribution_stops_at_it`.
2. **Attribution order and the routing table** (D521). The class is the first of correctness → ε → δ → Δpre → L_rep → irreducible whose term exceeds the band or cannot be judged. `src/kta/orchestrator/routing.yaml` (version 1, its hash recorded in every decomposition) maps class → rule / target / task / escalation / improvement class. It **replaces** judging rules 1–4 (no parallel path): ε → T4, δ → closed + escalate to you, Δpre → T1, L_rep → T2 (T1 without a reference), correctness → T6. New judging edges: rule 5 (escalated) and rule 6 (null rounds) to a new terminal state `closed` in machines.yaml. Tests: `test_routing_table_is_versioned_and_recorded`, `test_judging_rule_5_uncertified_solver_closes_and_escalates`, `test_judging_rule_6_null_rounds_close_the_case`, and the updated rules 1–4 in `test_orchestrator_step.py`.
3. **O5 fault-injection harness** (acceptance). Four deterministic faults planted into one accepted near-SOL bucket route to their class: degraded model → ε (T4), deleted template → L_rep (T1 without a reference), capped solver → δ (closed, escalate), failed check → correctness (T6). Test: `test_fault_injection_routes_to_the_right_class` (parametrized), with `test_the_base_bucket_is_accepted`.
4. **Accept and escalation rules of 12 §4** (D522, D523). Rule 3 reads `escalation.accept`; with no reference only a gap within the band of SOL accepts. Model error above `topk_model_error_rel` after `calibrations_first` T4s closes the case with `escalated: knowledge`; the summarize process marks a class `escalate: knowledge` when it recurs in `same_residual_cases` distinct cases. A missed canary is an inbox item. Tests: `test_accept_rule_reads_the_registry`, `test_model_error_after_calibration_escalates_to_knowledge`, `test_summarize_counts_routed_classes_and_escalates_recurring_ones`.
5. **Loop disciplines** (D525–D527; `src/kta/orchestrator/disciplines.py`). Mechanisms per round are derived from the chain/model/family diff, and coupled templates count once. A gain is credited only beyond the improvement band, attributed, and within one mechanism per round. Null rounds count toward `guard.null_round_limit`. A regression beyond the band is rolled back to the incumbent: acceptance is blocked for that round and retrieval prefers the incumbent family. Tests: `test_mechanisms_count_coupled_templates_once`, `test_gain_is_credited_only_beyond_the_band_and_attributed`, `test_a_regressing_round_is_rolled_back_to_the_incumbent`.
6. **Selection controls and exploration share** (D524; `solve_work.selection_arms`, `gap.selection`). Of the 8 measured points per bucket, 2 are random feasible points drawn from the enumerated space without the model. A copied assignment (the newest Solution of the family on another case) is measured in addition. Per-bucket results are recorded in the decomposition: model best, model's first e, random best, copied, model beaten by random. Tests: `test_selection_arms_draw_random_feasible_points_and_copy_a_solution`, `test_selection_controls_are_recorded_per_bucket`.
7. **Duplicate-proposal rejection** (D529; `TaskQueue.check`). An identical resubmission (same file names and blob hashes) after a rejection is rejected without running the done checks. Test: `test_an_identical_resubmission_is_rejected_without_running_checks`.
8. **Canaries** (D528; `src/kta/orchestrator/canary.py`). Each summarize batch plants the next fault kind into the newest decomposition's recorded inputs and re-classifies. Verdicts are caught, missed, uninformative or no_base, written as a Report `canary`. A missed canary stays in the inbox until that kind is caught again. Tests: `test_canaries_rotate_kinds_and_are_caught`, `test_a_missed_canary_escalates_to_the_user`, `test_no_decomposition_means_no_base_not_a_pass`.
9. **Every threshold from the controls registry.** The knobs of 12 §3/§4 marked "pending WP18" are now consumed (improvement band, mechanism attribution, null-round limit, one mechanism, exploration share, duplicate rejection, selection controls, canary rate, accept, case → knowledge, → user), and their `consumer` cells are updated. The gate checks that the WP18 modules hold no fractional literal.
10. **Views.** The case timeline API (`/cases/{id}`) gives each round's `gap_class` and `decomposition`. The Case page links "gap decomposition" for each round. The Overview no longer counts `closed` loops as solving.
11. Gate: `tools/kta_gate/specific_wp18.py`, registered in `specific.py`, plus the WP18 row in spec/gate.md. Spec: spec/schemas.md (GapDecomposition), spec/modules/orchestrator-cli.md "WP18", and the orchestrator README. Change log entry; review-queue entries for D520/D521, D522/D523, D524 and D528.

## Fixtures and simplifications

- No `# kta:fixture` in `src/`.
- Δpre and irreducible are always `not_assessed` today: no producer exists for `relaxed_pred_us` (WP19) or `irreducible_us`, so their share stays in L_rep. This is labelled in every record.
- Canaries plant faults into decomposition inputs, not wrong kernels into the checkers.
- Rollback restores the incumbent's family preference only; the model version is not pinned back (D527).

## Known issues

- The solve-loop work handlers changed (`work_solving` control arms, `work_building` arms, `work_judging` inputs) are type-checked and partly unit-tested (`selection_arms`), but no test drives a case through building → measuring → judging, because that needs a GPU worker. The pure `judge` is fully covered.
- The random arm on a very large space enumerates up to `EXHAUSTIVE_LIMIT` nodes, which costs CPU time in the solving state. Random-arm points may hit hardware walls and then fail to build; they are dropped from the measured set, not counted as a model loss.
- `escalation.level_choice`, the template-assurance refusal and the agent budget-reminder message are still "pending WP18" in the registry. They are outside the WP18 workplan bullets and not done here.
- "Claim or criterion change" escalation (12 §4) is not implemented beyond the existing fixed task card.
- `test_judging_rules_are_ordered_one_to_four` was renamed `..._one_to_six`, and WP9a's gate list was updated to match.

## Design interrogation

Full pass over the spec interface changes (GapDecomposition, judging rules 5–6 + `closed`, routing table, selection arms, duplicate rejection, canary Report). The adversarial second pass is due at the milestone (fresh context).

### M1: GapDecomposition and the routing table

1. *What*: a per-round record splitting the measured gap to SOL into five terms, plus the data table that turns the first significant term into the next action. It is not a Gap record (a missing-knowledge item) and not a per-unit residual (those stay in the judgement `units`).
2. *Claim*: P7. The gap routes the next action, so repair goes where the loss is (A5 attributability); paper Table 4 becomes a router.
3. *Depends on*: given: Bound (SOL), measured best, solver certificate, predictions. Assumed: L1 SOL ≤ any achievable time (G2), and that the model's prediction ≥ SOL. A negative L_rep shows when the assumption breaks.
4. *Scope*: solve-loop cases with measured buckets. Graph-level cases are out of scope (level choice is not done).
5. *Fails by*: ε absorbing selection slack (by design, D520); Δpre hidden in L_rep while not assessed; an uncertified solver blocking every later class; a routing edit that sends a class nowhere.
6. *Observable*: each term's `status` in the record; `routing@v:hash` in the record; the canary verdicts; the gate check that each route is a judging edge.
7. *Knob*: `guard.improvement_band`, `judging.model_ranking`; the table itself (versioned file).
8. *Repair*: the system loop edits routing.yaml (a new version); stored decompositions keep their version.
9. *Decides*: assistant default, needs user review (D520, D521). Alternatives not taken: δ as the measured-vs-predicted ranking slack; holding in judging instead of `closed`. Changing later costs little.

### M2: Accept rule (12 §4)

1. *What*: the rule-3 test. A case accepts if it is not worse than the reference (within the band) and |ε| < 10 % of T, or if the gap is explained as irreducible.
2. *Claim*: D-T11, SOL as the stopping criterion. Without it, results are accepted unexplained.
3. *Depends on*: the reference measured under the same protocol (given, D284); the band (assumed adequate, set by X6).
4. *Scope*: per bucket; every bucket must accept.
5. *Fails by*: no reference, so a case with a large L_rep never accepts and closes by null rounds (D522). A noisy reference accepts a slower kernel within the band.
6. *Observable*: `accepted` per bucket and the class in the record; closed cases in the inbox.
7. *Knob*: `escalation.accept` (all three fields).
8. *Repair*: the user changes the knob (a controls version); re-judging needs a new round.
9. *Decides*: assistant default, needs user review (D522, D523). The alternative not taken is the vacuous-reference reading.

### M3: Disciplines (credit, null rounds, rollback)

1. *What*: per-round bookkeeping over the incumbent. It is not a scheduler and does not forbid multi-mechanism changes; it denies them credit.
2. *Claim*: D-T12, attributable progress and monotone best measured time (02 §6.1).
3. *Depends on*: the basis being recorded each round (given); couplings in the pool (assumed sparse but correct).
4. *Scope*: case loop rounds ≥ 2.
5. *Fails by*: a task that changes generator and template together, which is unattributable and counted as two; a noisy regression rolling back a real gain; an agent splitting one idea across rounds to farm credit (each split must still beat the band).
6. *Observable*: `discipline` in each record (mechanisms, gain, credited, rolled_back, null_rounds).
7. *Knob*: `guard.improvement_band`, `guard.mechanism_attribution`, `guard.one_mechanism_per_round`, `guard.null_round_limit`.
8. *Repair*: the knobs; the user restarts a closed case.
9. *Decides*: assistant defaults (D525–D527). The alternative not taken is agent-declared mechanisms, which would be gameable.

### M4: Selection arms

1. *What*: measured control points (random feasible, copied). It is not part of the model's shortlist.
2. *Claim*: E4 / D-T13, a solver that adds nothing is noticed (the paper could not isolate the solver's gain).
3. *Depends on*: that enumeration can sample the space (given for spaces below EXHAUSTIVE_LIMIT; a bounded walk beyond that); that a prior Solution exists for the copied arm (often not).
4. *Scope*: every solve with candidates.
5. *Fails by*: the random sample being biased for huge spaces (DFS order under a node bound); random points hitting walls; spending GPU on controls.
6. *Observable*: `selection` per bucket; `random_n`; `model_beaten_by_random`.
7. *Knob*: `guard.exploration_share`, `guard.selection_controls`.
8. *Repair*: set exploration_points to 0 to stop the random arm; the system loop reads `model_beaten_by_random` statistics.
9. *Decides*: assistant default, needs user review (D524). The alternative not taken is random draws from the shortlist.

### M5: Canaries

1. *What*: planted faults on recorded inputs, one per batch. They do not test the kernel checkers.
2. *Claim*: D-T17, empty checks are noticed.
3. *Depends on*: a decomposition in the window (else no_base); a base not already of the expected class.
4. *Scope*: decomposition and routing code and the knobs in force.
5. *Fails by*: always uninformative (every base of one class); a knob change that blinds routing. That is exactly what `test_a_missed_canary_escalates_to_the_user` shows.
6. *Observable*: `canary` Reports with verdicts; the inbox item `canary_missed`.
7. *Knob*: `guard.canary_rate`, `escalation.to_user.on_canary_missed`.
8. *Repair*: fix the routing or knob; the item clears when the kind is next caught.
9. *Decides*: assistant default, needs user review (D528).

### M6: Duplicate-proposal rejection

1–9 in short: a per-task digest of the submission blobs. It serves "retrying the same thing" (12 §3). It fails when an agent changes one byte to dodge it; that shows as repeated rejections of the same checks (the existing inbox `repeated check failure`). Knob: `guard.duplicate_proposal_rejection`. Assistant default (D529); the alternative not taken is digests across tasks.
