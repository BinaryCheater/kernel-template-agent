# WP15 delivery: Template effects and the declarative hardware model

Branch `wp/WP15`, code stage (D320): no real run, no GPU job, no experiment. Decisions D460–D474. Design source: docs/design/02 §3, §4, §5.1; D324, D325 (5).

## What was done

Every capability below is shown by unit tests on the control host only (`deliveries/WP15.evidence.json`, one code-stage claim, no store record). None has run against real hardware.

1. **Template effects** (D460, D461). `Template.cost` → `effects` = transactions (operation class `kind`, optional `kind_map`, `count`, per-transaction `amounts`, `src`/`dst`, `when`), storage (`level`, `scope`, `bytes`) and overlap (`between` selectors, `when`, `inflight`, `trips`): `src/kta/core/schemas/effects.py`, spec/schemas.md §4.2.1. The loader, `validate_template` (effects expressions, storage levels, `unpriced_operation_class` warning), duplicate detection, retrieval by resource and the formulation blocks all read effects. Each physical transaction is declared once, by the step that performs it. This fixes the WP5 known issue: `compute_instruction_selection@2` declares the contraction, `async_transfer@1` the operand traffic, `output_tiling@2` the compulsory DRAM traffic and the launches. Test: `test_gemm_seed_chain_priced_by_l1_with_per_unit_sol`.
2. **Every seed Template migrated** (D468). `scripts/migrations/WP15_effects.py` is idempotent (`--check` mode) and replaces only the `cost:` block, keeping the rest of each file byte for byte. It was run on all 37 seed Templates (7 in `templates/`, 30 in the WP10a references); a second run changes nothing. Pattern `sync` gained `warps`, and the two GEMM family chains bind `p.warps`. Tests: `test_every_seed_template_validates_with_effects`, `test_migration_is_idempotent_and_keeps_the_rest_of_the_file`.
3. **Immutable records upcast on read** (D461). `KindSpec.upcasts`, `upcast_body`, `parse_body(..., schema)` and `Record.body_model()`. A schema-1 Template record keeps its stored body and its ID, and reads as legacy `unit:<u>` transactions that price exactly as the old cost terms did. The locked WP5 acceptance tests pass unchanged on that legacy path. New versions: Template 2, HwModel 2, Prediction 2. Test: `test_schema_1_cost_record_upcasts_on_read_and_keeps_its_id`.
4. **Declarative hardware model** (D462, D463). `HwArch` is the architecture class: scopes, params, resources (kind, scope, amount, peak, latency, max in-flight, ncu counter names), walls with cliffs, operation classes with reservation tables (optionally SASS classes), table terms, efficiency, interactions and the composition rule. `HwModel` schema 2 is the chip instance: `arch`, a `provenance` entry for every value, instance tables, efficiency and interactions. Expressions use the restricted language with the roots `hw`, `tx`, `f` and `tbl`, and HwArch refuses anything outside them. `MachineModel.build` resolves the instance on its class (`src/kta/models/machine.py`). Spec: spec/schemas.md §3 and §4.6.1.
5. **L1 pricing** (D464, D465, D471; `src/kta/models/l1.py`). Per-resource busy time, pair bounds, recurrence bounds, serial terms, interactions, wall checks (no_launch / lower_occupancy residency), per-resource SOL (`sol_us`) and the total. Resources without a peak (infinite capacity) and operation classes without a reservation table are counted in `unpriced` / `unmodelled` and carried into `Prediction.unpriced`. They are never silently zero-cost. `bound` is rebuilt on L1. `UnitModel` composes through `l1.compose` and adds `predict_l1`. `solve` prices every point with L1 and refuses priced effects on a class-less HwModel. The MIP objective uses reservation-table rows (`formulation.work_terms`, D472). The orchestrator and the WP7 tools resolve `MachineModel` from the store (`load_machine`). Tests: `test_pair_and_recurrence_bounds_and_serial_terms`, `test_unpriced_class_and_unmodelled_resource_are_counted_not_free`, `test_mip_rows_match_l1_amounts`, `test_effects_without_architecture_class_are_refused`.
6. **Changing one wall or one peak changes the prediction without code changes.** The test changes `dram_bytes_per_s` in the instance data and the `smem_per_cta` wall limit in the class data (the latter makes the point infeasible with the wall named). Test: `test_changing_one_peak_or_wall_changes_the_prediction`.
7. **GB10 class and instance seeded** (D467, D474). `knowledge/seed/hardware/arch_sm12x.yaml` holds 9 resources, 3 walls, 22 operation classes and a bank-conflict table. `model_gb10.yaml` (gb10@1) labels every value: device attributes and CUDA-guide constants are `documented`. Bandwidths, clock, latencies, tensor rates and the bank-conflict table are `documented` from the upstream calibration contract, cited with file hash and commit; they were measured upstream, not by KTA. `sfu_ops_per_cycle_per_sm`, `mma_latency_cycles` and `smem_queue_depth` are `default`. The CTA dispatch rate (`launch`) is unmodelled and reported. `kta init` imports both files. `measure_peaks` will attach measured peaks to this instance with provenance. Test: `test_seed_imports_the_gb10_class_and_instance`.
8. **Interference microbenchmarks** (D469; `src/kta/measure/interference.py`). Probes for 6 operation classes; `plan` defines three kernels per pair (A alone, B alone, A+B interleaved). The `InterferenceMatrix` artefact schema counts coverage (measured / declared independent / unmeasured). `measure_pair` exists but has not run. Test: `test_interference_plan_defines_three_jobs_per_pair`.
9. **Model versions and the regression set** (D470). Record kinds `ModelVersion` (parameter table refs, per-level simulator commits, change kind, regression results, hold-out decision) and `RegressionSet` (at least two configurations per kernel). Test: `test_regression_set_needs_several_configurations_and_model_version_is_a_record`.
10. **Interface for WP16 and WP17.** spec/modules/formulation-solve-models.md "Hardware model and L1" states what L2 and the projection compiler consume: `MachineModel`, `EvalEffects`, `Parts`/`compose`, `Formulation.transactions/storage/overlaps` and `work_terms`. It also states that L1 is the steady-state limit L2 must reproduce.
11. Gate: `specific_wp15` (`tools/kta_gate/specific_wp15.py`, D473) and a WP15 row in spec/gate.md. Change log entry in docs/changelog.md; review-queue entries for D460, D461, D463, D464, D466, D468, D474.

## Fixtures and simplifications

- Simplifications, each a decision: recurrence bound per executor (`trips`) with the smallest latency per group (D464); MIP relaxes pair/recurrence bounds and walls (D472); UnitModel kept as the calibration overlay instead of folding fitted values into HwModel versions (D466).

## Known issues

- L1 ties: at a resource bound (e.g. 4096³ GEMM, tensor-bound) many configurations predict the same total; this is the steady-state bound, not a bug. Ranking among them needs L2 (WP16).
- The GB10 instance has no KTA-measured value; `launch` (CTA dispatch) is unmodelled, so every GEMM prediction carries `unpriced = {"resource:launch": …}`.
- The C tile store through L2 is not declared (only the compulsory DRAM bytes); cp.async does not reserve shared memory because `shared_resource_binding@1`'s access count covers cp.async writes and ldmatrix reads together (D460).
- Variable-chosen kinds (e.g. the WP5 test family's `mech`) make `work_terms` not exportable; such spaces use enumeration.
- A store that imported the pre-WP15 seed reports conflicts on `kta init` (D468); no store with real data exists.
- The effects of the 30 reference Templates translate their v1 cost; they have not been checked against the references' SASS. The 02 §3 granularity statistics are not built.
- The interference probes and the measured-peak attachment have not run on a GPU; probe kernels have not been compiled.
- `tools/kta_gate/specific.py` was already over 500 lines; WP15's checks live in `specific_wp15.py`.

## Design interrogation

Full pass over the spec interface changes. Each mechanism gets the nine questions; the adversarial second pass is due at the milestone.

### M1: Template effects (spec/schemas.md §4.2.1)

1. *What*: the cost face of a Template written as transactions, storage and overlap statements in the transaction vocabulary. It is not a per-unit work estimate, and it holds no hardware number.
2. *Claim*: one calibration benefits all templates (D-T2); the MIP and the simulator can be derived from the same data (R1).
3. *Depends on*: operation-class names shared with the hardware model (an assumption: the names are a stable vocabulary); chain bindings for counts (given: D246).
4. *Scope*: steady-state kernels whose transactions can be counted per refined instance. Data-dependent control flow is expressible only through `when`, and only as a coarse approximation.
5. *Fails by*: double declaration of one transaction by two steps; a missing declaration (the WP5 issue); an agent choosing a cheap kind to look fast.
6. *Observable*: L1 `per_tx` attributes time per step. `unpriced` counts kinds the model does not know. A double declaration shows as excess busy time against the SOL and, after real runs, against the SASS census (obligation O-c).
7. *Knob*: none at runtime. The vocabulary lives in the HwArch data.
8. *Repair*: a new Template version or seed migration. A stored record upcasts and is never rewritten.
9. *Decides*: assistant default (D460). The alternative not taken is replace semantics for refined transactions. Changing later costs medium (schema + seed).

### M2: Schema upcasts (spec/schemas.md §1)

1. *What*: version-indexed body transforms applied on read. It is not a data migration.
2. *Claim*: records are immutable and old evidence stays readable (round-4 rule).
3. *Depends on*: the stored `schema` field (given). The assumption is that every upcast is total on old bodies.
4. *Scope*: every kind.
5. *Fails by*: an upcast that throws on an unusual old body; a reader that uses `rec.body` raw and sees the old shape.
6. *Observable*: `InvalidBody("cannot upcast …")` at read time. Raw-body readers that model-validate get the Template before-validator; other kinds only add optional fields.
7. *Knob*: none.
8. *Repair*: fix the upcast function. Stored data never changes.
9. *Decides*: assistant default (D461), shared with WP14. The alternative not taken is rewriting stored records (forbidden).

### M3: Hardware model class + instance (spec/schemas.md §4.6, §4.6.1)

1. *What*: declarative resources, walls, operation classes, tables, efficiency, interactions and composition, plus instance numbers with provenance. It is not a simulator; L2 and L3 consume it.
2. *Claim*: a single declarative source (R1, R3); co-design operability (wall moves without code changes).
3. *Depends on*: given: the WP7 per-unit peak definitions. Assumptions: reservation tables in warp-instruction terms are adequate at L1, and the upstream contract approximates KTA's measurements.
4. *Scope*: GB10 / sm12x. Other chips need their own instance, and possibly a new class.
5. *Fails by*: a documented value far from reality; a class with a missing operation class (silent infinite capacity); provenance written as boilerplate.
6. *Observable*: `Provenance.status` per value; `unpriced/unmodelled` counts per prediction; after real runs, ModelVersion regression results.
7. *Knob*: the data itself (values, walls, tables), versioned as records.
8. *Repair*: the maintenance loop of 02 §4. Largest-error case → microbenchmark → new instance or class version with a ModelVersion (adapter_fix / machine_model_change) → hold-out → admit or roll back (WP16).
9. *Decides*: assistant default (D463, D467, D474). The alternative not taken is one flat model per target (D-T10). Changing later costs low.

### M4: L1 composition and unpriced reporting (spec/modules/formulation-solve-models.md)

1. *What*: the steady-state lower-bound combination of resource busy times, pair and recurrence bounds, serial terms and interactions. It is not a schedule.
2. *Claim*: the MIP is a relaxation of the simulator (02 §5.2). Per-unit SOL, busy time and total are reported separately (D-T11).
3. *Depends on*: modulo-scheduling bounds (given). Assumptions: overlap statements are the only coupling, and the smallest latency per group keeps the bound optimistic.
4. *Scope*: loop-dominated kernels are tight. Latency-dominated kernels are loose; there L2 ranks.
5. *Fails by*: ties at a bound hiding real differences; an over-tight bound (a non-optimistic term) breaking MIP ≤ L2; unpriced work making a bad configuration look fast.
6. *Observable*: `Prediction.bounds` and `unpriced`; the bottleneck name; the WP17 consistency check (MIP ≤ simulator on sampled points).
7. *Knob*: proposed registry rows (see "Needed changes"); the composition rule name in HwArch.
8. *Repair*: change `compose` (one function), re-run the regression set, and record a ModelVersion.
9. *Decides*: assistant default (D464, D465). The alternatives not taken are refusing to price incomplete models, and an additive serial-only model. Changing later costs low.

### M5: Interference matrix, ModelVersion, RegressionSet

1. *What*: record and artefact schemas plus job definitions for model maintenance. They are not results.
2. *Claim*: completeness is measured coverage (D-T14), and ranking needs several configurations per kernel (02 §4).
3. *Depends on*: assumption: probe kernels isolate one class each.
4. *Scope*: the operation classes that have probes (6 today).
5. *Fails by*: probes that do not isolate their class; a regression set with one configuration per kernel; a ModelVersion admitted without hold-out.
6. *Observable*: `InterferenceMatrix.coverage()`; RegressionSet validation; `ModelVersion.admitted` stays None until regression results exist.
7. *Knob*: `min_configurations` (default 2).
8. *Repair*: new probe or new set version; nothing is overwritten.
9. *Decides*: assistant default (D469, D470).
