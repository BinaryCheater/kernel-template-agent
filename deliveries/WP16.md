# WP16 delivery: Transaction-level simulator, what-if and regression scoreboard

Branch `wp/WP16`, code stage (D320): no real run, no GPU job, no experiment. Decisions D500–D512. Design source: docs/design/02 §4 (L2, L3, "Sustained saturation and walls", "Maintenance as a software artefact"), §5.1; D324, D325, D328. Built on WP15's `MachineModel`, `EvalEffects` and L1.

## What was done

Every capability below is shown by unit tests on the control host only (`deliveries/WP16.evidence.json`, one code-stage claim, no store record). None has run against real hardware or a real measurement.

1. **L2 simulator** (D500–D503, D505; `src/kta/models/l2graph.py`, `src/kta/models/l2.py`). `simulate(effects, mm)` builds a per-CTA transaction graph from the evaluated effects: transactions are divided by the CTA count and by the loop statement's trips. The phases are prefix, load, sync, compute and epilogue. The edges are load → sync → compute after the class latency, and compute → load `inflight` trips later (slot reuse). Resident CTAs run in lockstep as one wave. The wave is list-scheduled on FIFO resources of the `MachineModel`, and waves follow each other. Tail waves use only the occupied SM share. Outputs: total, per-resource busy time (equal to L1's), idle per resource in the five categories of 02 §4 (other unit, data, sync, prologue/epilogue/tail, wall), stall reasons and metrics under ncu names, the occupancy timeline (waves with CTA counts) and merged busy intervals per wave kind. The model string is `l2:1:<MachineModel.version>`. The simulator is deterministic and takes about 6 ms for the 4096³ GEMM (1024 CTAs, 11 waves, 128 trips). Tests: `test_gemm_seed_family_simulated_at_l2_with_a_timeline` (the real seed GEMM formulation, all three Case shapes), `test_the_l2_result_is_stored_as_a_report`.
2. **L1 = steady-state limit of L2** (WP15 obligation O-a). On a loop-dominated fixture (48 CTAs in one wave, four stages, K up to 65536), the relative gap shrinks to 0.06 % at 2048 trips, and L1 ≤ L2 everywhere. With shallow pipelines (S = 3) L2 stays above L1 by more than 10 % however many trips run: L1's recurrence bound counts latencies only, while the real cycle also holds the producers' busy time. Tests: `test_l1_equals_the_steady_state_limit_of_l2_on_a_loop_dominated_fixture`, `test_with_shallow_pipelines_l2_exceeds_l1_by_the_recurrence`.
3. **What-if and shadow price** (D504; `src/kta/models/whatif.py`). `what_if(effects, mm, peaks=…, walls=…)` re-simulates on an in-memory moved model (`moved`; unknown names raise KeyError) and reports the shadow price: the base bottleneck's idle time removed, plus the change in total time. `simulate` itself re-runs with the binding residency wall moved to fit one more CTA per SM, and books the idle that removes as `wall`. A no-launch wall makes the point infeasible: no cost, shadow price None. `record_l2` / `record_what_if` store Reports. On the walled fixture (64 kB shared memory per CTA, so one CTA per SM, 22 waves), relaxing `smem_per_sm` to two CTAs per SM gives a shadow price of about 29 µs. Tests: `test_what_if_shows_a_non_zero_shadow_price_on_a_walled_fixture`, `test_what_if_on_a_peak_and_on_an_unknown_name`, `test_a_no_launch_wall_is_infeasible_not_a_cost`, `test_unpriced_operation_classes_are_carried_into_l2`.
4. **L3 adapter** (D506; `src/kta/models/base.py`, `src/kta/models/l3.py`). The `L3Simulator` protocol and `ExternalSassSimulator`. `job()` defines a `shell` Job on the cpu pool that runs the research bundle's `tools/simulate.py` (`kernel-lab/exports/gb10-simulator-calibration-20261020-v2`) with the cubin as job input; the bundle is never imported. `simulate()` raises NotSupported until that job has run for real. Test: `test_l3_adapter_defines_an_executor_job_and_is_not_supported_until_run`.
5. **Regression scoring and scoreboard** (D507–D509; `src/kta/models/regression.py`). The module provides `spearman` (average ranks for ties), `results` (per kernel: rank correlation and the median relative error of the total and of each resource's busy time), `summarise` (all cases and hold-out cases), `admit` (knob `model.version_admission`, new in the controls registry, 12 §7, set_by X10), `observe` (a stored RegressionSet → observations; Measurement medians, measured busy from the Profile's ncu pct-of-peak metrics), `record_version` and `scoreboard`. `RegressionResult` gains `holdout`, `predictions` and `measurements` (optional fields). Tests: `test_spearman_ties_and_degenerate_inputs`, `test_scoring_errors_per_resource_and_admission`.
6. **API and web views** (D510, D511). `GET /model/scoreboard`, `GET /model/versions/{id}/timeline?kernel=` (`src/kta/api/modelview.py`) and the page `/model/scoreboard` (`web/src/pages/Scoreboard.tsx`). The page has the version × kernel table with origin chips (FIXTURE for non-real data), admission, ρ and error columns. Under it, per configuration, the first wave's L2 busy intervals per resource and the predicted and measured totals. `scripts/seed-dev` writes the fixture (`tools/kta_devseed/models.py`). Test: `test_scoreboard_renders_on_fixture_data_marked_fixture` (API on the fixture). `npm run build` passes. The page was opened in the browser pane on a seed-dev store (`$KTA_DATA/dev/WP16-fixture`). The table, the origin chips and the per-configuration timelines rendered.
7. Gate: `specific_wp16` (`tools/kta_gate/specific_wp16.py`, D512) and a WP16 row in spec/gate.md. Spec: spec/modules/formulation-solve-models.md "L2 transaction-level simulator" and "What-if, L3 and the regression scoreboard", spec/schemas.md (RegressionResult), spec/modules/api-web.md (views and page). Change log entry; review-queue entries D500/D501, D503, D509.

## Fixtures and simplifications

- `tools/kta_devseed/models.py` (`# kta:fixture`): the scoreboard fixture. Its predictions are real L2 runs on the seed GB10 model over closed-form GEMM effects. Its "measured" times are synthetic: L2 on a model with the L2 peak × 0.85, times a ±3 % pattern. Every record has origin fixture, and the page shows FIXTURE. No `# kta:fixture` in `src/`.
- Simplifications, each a decision: resident CTAs in lockstep, with no CTA skew and no overlap between waves (D501); independent FIFO booking per resource (D502); per-phase latency = the largest class latency in the phase (D500); the stall-name mapping is approximate and in µs, not samples (D505).

## Known issues

- L2 > L1 on shallow pipelines (S ≤ 3 in the GEMM fixture): L1's recurrence bound (D464) counts only latencies. L1 stays optimistic, so the MIP is still a lower bound, but the projection is loose there. WP19's MIP ↔ L2 check (X11 thresholds) will see this gap.
- The phase assignment comes from patterns and the loop statement. Effects that hide the loop structure (no two-selector overlap with `trips`) run as one trip per CTA, with a note in the result.
- No in-kernel timestamps exist, so the measured side of the timeline view is the total time only. Per-resource measured busy time needs a Profile with the ncu pct-of-peak metrics.
- The CTA dispatch resource `launch` is still unmodelled (WP15), so every GEMM L2 result carries `unmodelled = {"launch": <CTAs>}`.
- The browser check was visual only, on fixture data. Nobody has reviewed the page's layout.

## Design interrogation

Full pass over the spec interface changes. Each mechanism gets the nine questions; the adversarial second pass is due at the milestone.

### M1: L2 simulator (spec/modules/formulation-solve-models.md "L2")

1. *What*: a deterministic list schedule of a chain's evaluated effects, per CTA and per main-loop trip, on the declarative hardware model's resources. It is not a SASS-level simulator (L3) and not a cycle-accurate one.
2. *Claim*: pre-compile bottleneck analysis and virtual wall moves (02 §4 L2 row); ranking where L1 ties (WP15 known issue); "L1 is the steady-state approximation of L2".
3. *Depends on*: given: WP15's MachineModel and EvalEffects, and L1's per-transaction times. Assumptions: effects are whole-kernel counts that divide evenly over CTAs and trips; the loop statement names the producer and consumer groups; resident CTAs behave alike (lockstep).
4. *Scope*: loop-structured kernels with one main loop per CTA (GEMM-like). Kernels with several loops, data-dependent trips or persistent CTAs are approximated as one loop or one trip.
5. *Fails by*: a phase assigned wrongly by pattern; skewed CTAs (lockstep hides contention between waves); a template that declares counts per CTA instead of per kernel (double division); an agent choosing effects that make L2 look idle-free.
6. *Observable*: `notes` (assumed inflight, one trip, unbounded residency); `busy_us == L1 busy` (a test); `l1_total_us` next to `total_us`; regression errors per resource once measured (scoreboard).
7. *Knob*: none at runtime; `SIM_VERSION` versions semantics. The thresholds that judge L2 against the MIP are WP19's (X11).
8. *Repair*: a regression case with the largest error → per-resource counters → a change to `l2graph.py` (bump `SIM_VERSION`, labelled "adapter fix") or to the hardware model (a new ModelVersion) → hold-out regression → admit or roll back (D509).
9. *Decides*: assistant default (D500–D503). The alternative not taken is an explicit per-CTA graph declared in Template effects (a schema change). Changing later costs medium.

### M2: What-if and wall attribution (D504)

1. *What*: re-simulation with a resource peak or wall limit moved in memory, and the bottleneck idle the move removes. It is not a model change and writes no hardware record.
2. *Claim*: 02 §4 "shadow price" separates scheduling problems from hardware limits, and gives the co-design value of a wall.
3. *Depends on*: L2's idle attribution; the wall model of WP15 (`lower_occupancy` residency, `no_launch` legality).
4. *Scope*: walls and peaks the hardware model declares. Moving a wall that is not modelled is a KeyError, not a silent no-op.
5. *Fails by*: shadow price read as a speed-up guarantee (it is L2's, not hardware's); a negative price when a peak move shifts the bottleneck; wall attribution taken from the wrong category.
6. *Observable*: `what_if` Report with both models' versions and both idle breakdowns; `delta_total_us` next to the price; the note "wall … binds residency …".
7. *Knob*: none. The move size for automatic wall attribution is one more CTA per SM (fixed in code, D504).
8. *Repair*: compare the shadow price with a real wall relaxation where the hardware allows it (e.g. fewer stages); otherwise through the regression loop of M1.
9. *Decides*: assistant default (D504). Alternatives: attribute wall idle by a rule without re-simulation, or move the wall to its limit instead of +1 CTA. Changing later costs low.

### M3: L3 adapter (D506)

1. *What*: a protocol and a job definition for the research repository's SASS-level simulator as an external tool. It is not an import, and it is not a working L3 path yet.
2. *Claim*: post-compile reranking and diagnosis (02 §4 L3 row); "disagreement between adjacent levels is a diagnostic".
3. *Depends on*: given: the bundle's `tools/simulate.py` entry and the Executor's `shell` job kind. Assumptions: the tool accepts a cubin and launch configuration, and its output can be mapped to SM and bus terms (unchecked).
4. *Scope*: GB10 binaries the bundle's simulator supports.
5. *Fails by*: returning a made-up result; importing the research code; a format mismatch once it runs.
6. *Observable*: NotSupported with "pending real run"; the gate checks that nothing under `src/kta` imports the bundle.
7. *Knob*: none (`timeout_s` in the constructor).
8. *Repair*: the first real job fixes the argument list and the parser; the delivery of that run updates this adapter.
9. *Decides*: assistant default (D506). Changing later costs low.

### M4: Regression scoring, admission and RegressionResult fields (D507–D509)

1. *What*: per-kernel rank correlation and median relative errors (total and per resource) of a model version against measurements, with a hold-out admission decision. It is not the per-loop judging rule 2 (the solve loop's model-off check).
2. *Claim*: "what the solver relies on is ranking" (02 §4 Maintenance); model changes are admitted on evidence, not by default.
3. *Depends on*: given: Measurement and Profile records with ncu metrics. Assumption: `pct_of_peak_sustained_elapsed` of the first counter measures the same busy time L2 predicts.
4. *Scope*: kernels with ≥ 2 configurations measured (RegressionSet enforces it).
5. *Fails by*: rank correlation inflated by easy configurations; hold-out cases that leak into fitting; admission on few cases; a version marked admitted without hold-out (prevented: `admit` returns None).
6. *Observable*: the scoreboard (per version × kernel), `summary` keys with `holdout_` prefix, `admitted` None/True/False.
7. *Knob*: `model.version_admission` {rank_min 0.7, rel_error_max 0.25}, controls registry 12 §7, set_by X10.
8. *Repair*: a rolled-back version keeps its record; the next version cites `previous`; thresholds move by a controls version.
9. *Decides*: assistant default needing user review (D509). Alternatives: reuse judging rule 2's thresholds, or Kendall τ. Changing later costs low.

### M5: Model views (D511)

1. *What*: read-only endpoints and a page over ModelVersion records and stored l2_simulation Reports. They are not a computation endpoint: nothing is simulated on GET.
2. *Claim*: 02 §4 "Views: regression scoreboard; per-kernel timeline (predicted over measured)".
3. *Depends on*: ModelVersion records with `predictions` links (D507).
4. *Scope*: any target; fixture and real rows side by side, each marked.
5. *Fails by*: fixture rows read as evidence; a timeline missing because a version stored no prediction link.
6. *Observable*: the origin chip per row and the `fixture` flag; empty configuration timelines show no intervals.
7. *Knob*: none.
8. *Repair*: view-only; data problems are repaired in the records' producer.
9. *Decides*: assistant default (D511). Changing later costs low.
