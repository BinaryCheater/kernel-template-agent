## What was done

### Part A — agent proxy (D580–D586)

- **System configuration** (`src/kta/core/sysconfig.py`, D580): `<data dir>/system/config.json`, separate from the controls registry. Holds the proxy override, `credentials_from_secrets`, `no_proxy_extra`, per-provider `proxy: required | off` and `check_hosts`, per-worker `intake_proxy`. Revisioned; written only by `POST /system` with the operator token, the revision the author read and a reason; each write leaves a HumanAction `set_system`. URLs with user:password are refused.
- **Detection** (`src/kta/core/proxy.py`, D582): `scutil --proxy` (HTTPS, HTTP, SOCKS when enabled) → `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` in either case → `http://127.0.0.1:7897`. The override wins. Detection runs at each step and its source is recorded. `http`, `socks5` and `socks5h` URLs are accepted.
- **Policy** (D583): codex and claude_code `required`, pi and deepseek_harness `off` (your defaults). A provider the table does not name is `off`. I kept the policy to `required | off`: an `optional` setting would amount to a silent direct fallback.
- **Injection** (D581): proxy variables are still not on `guard.ENV_WHITELIST`. `guard.agent_env(..., proxy_vars=ProxyPlan.env)` adds them only for a `required` provider, and only all eight together: `HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, the three lowercase forms, `NO_PROXY` and `no_proxy`. NO_PROXY always holds `127.0.0.1,localhost,::1` and the `KTA_API` host. The runner's own shell variables never reach the agent.
- **Fail closed** (D584, D585): the launcher runs `proxyplan.host_check` on the agent host before it prepares the workspace. The check covers the proxy port, then a CONNECT (HTTP or SOCKS5) and a TLS handshake per API host, with one retry per host. It sends no API request. If the check fails:
  - the launcher reports `refused` and the CLI never starts;
  - the runner writes a Report `proxy_preflight`, trips the breaker (ops pointer `proxy:status:<provider>`) and raises `ProxyUnavailable`;
  - `kta runner` abandons the attempt and leases no further task for that provider;
  - the Inbox shows "Proxy preflight failed" with the Report.

  A passing Test on the Settings page clears the breaker. For an `off` provider the launcher refuses the start if any proxy variable is present.
- **Traceability** (D586):
  - `AgentRun.proxy` records used, policy, scheme, host, port, source, no_proxy, the credentials flag and the preflight result. The context manifest shows the proxy variables.
  - Credentials live only in the agent host's `secrets.env` as `KTA_PROXY_USERINFO`. They are added to the CLI's environment there, and the manifest shows them as `<provided>`.
  - The secret scan and the log redaction gained a `proxy_userinfo` pattern.
- **Workers** (D590): an optional `intake_proxy` per worker, default off, stored and editable. It is not applied yet, because intake jobs are still dry-run plans (D569).

### Part D — agent workflow view (D593–D597)

- **Page `/workflow`** ("How does an agent task run, and what configures each step?") is in the sidebar under Intervene, next to Agents. It has a tab per task type T1–T6 and a pipeline of seven nodes: created by → task card and inputs → prompt assembly → session (new or resume) → agent run → done checks → accept, retry or escalate.
- **The pipeline is derived** (D593) by `GET /workflow` (`src/kta/api/workflow.py`) from these sources:
  - creators: `creates_task` transitions in `machines.yaml`, plus `TaskRequest("Tn"` call sites scanned from `kta/orchestrator` (calibrate makes T4 and T5; improve makes T3);
  - done checks: `DONE_CHECKS`, each with its function's source line;
  - session rules: the `Decision` reasons of `sessions.decide`, read from its AST in order;
  - retry and escalate edges: the task lifecycle in `machines.yaml`;
  - everything else from the profile record and the controls registry.

  Only `NODE_KNOBS` (which knobs act at which node) is hand-kept; a test checks its ids against the registry.
- **Every node is clickable:**
  - templates (prefix, step-Tn, messages, NOTES seed, CLI config.toml) open in a text editor with a live TASK.md preview, rendered by `cards.task_md` for a sample card or a real TaskCard ID;
  - skills (SKILL.md) open in a text editor too;
  - model, effort, provider and CLI version are editable fields;
  - knobs are edited in place and written as a new controls version (D597);
  - the proxy policy is written to the system configuration;
  - done checks and invariants are read-only and show their source.
- **Edits never mutate a profile** (D594). "Save draft version" writes a new AgentProfile version of the same name (`refs.base`, the operator as author, a HumanAction `draft_profile`) and shows the diff (fields plus unified diffs of templates and skills). The base record and `current_profile` stay as they are. Viewing another version shows its diff against the version in force.
- **Placeholder check** (D596): a `$name` that no renderer provides is an error in the preview before saving, and the save is refused with 400. A provided placeholder the template no longer uses is a warning.
- **Approval** (D595): "Approve draft" calls `approve_profile` and builds the batch `<name>-v<version>`. New tasks whose card names the approved profile use that batch (`runner.open_batch`); work units already running keep theirs, and past runs keep their profile version.
- **Model and effort are profile-wide.** AgentProfile has no per-task-type model, so the page says so instead of pretending otherwise. Changing that needs a schema change (review queue D594).
- **Checked in the browser pane** against the fixture store: the pipeline renders for T1–T6. Typing `$owner` into step:T1 showed "step:T1: $owner is not provided" before any save. Save and approve were not clicked there because there is no operator token on this machine and I did not create one. The API tests cover save, diff and approve.

## Known issues

- **Agent CLIs run on spark, which cannot reach the Mac's Clash (D592, needs your decision).** `config/kta.toml` has `[agents] worker = "spark"`. The injected `http://127.0.0.1:7897` therefore means spark's own loopback, so every Codex launch will be refused (fail closed) until one of these is done:
  - (a) run agent CLIs on a `local` worker on the Mac. This matches "the agent runner runs on the Mac" and is a config change only;
  - (b) a proxy on spark plus an override;
  - (c) an `ssh -R` port forward.

  I changed nothing on spark.
- A failed launch preflight abandons the attempt. That counts as one attempt (D584): returning the task to `queued` without counting would need a new machines.yaml transition.
- The worker Test can wait in the Executor queue up to `[executor] queue_timeout_s` when the worker's cpu pool is busy.
- The per-worker intake proxy is stored and shown but not applied (D590): nothing submits intake jobs yet.
- Part D: model and effort are per profile, not per task type (D594). cli_flags, isolation, auth, allowed commands and the skill list per type are shown but not editable.
- Part D: the batch fallback (D595) applies only to new work units without their own batch; a task created under an experiment batch keeps it.
- The System tab does not refresh the "Last preflight" column after a Test; the Test result row shows the outcome.
- The real run also wrote a failed Report for pi (`34cf2310…`, policy off, nothing to check). Since the next commit, the Test skips `off` providers and writes nothing for them.
